面向教育场景的离线课程处理、在线图片推理与实时语音三条链路。 总览用于识别平台边界，详图用于核对每条链路的执行顺序。

结论

平台边界合理，但必须拆开表达控制关系与业务流程

一张图同时承载 30 余组关系线会掩盖真实调用顺序。新版按业务用途拆图， 并补齐课程媒体目录、在线 Base64 边界和现有 ai_quality 聚合能力。

第一版不引入 Kubernetes，不把上游流媒体处理纳入平台。

  1. 总图连线过载总览只保留三条业务主链路，详细关系下沉到独立视图。
  2. 课程媒体缺少统一所有权平台下载 T/S/P 一次，并共享 /data/course/{course_job_id}。
  3. 在线输入边界需固定在线接口直接接收 Base64 图片，不承担持续视频流处理。
  4. 复合视觉能力不可遗漏ai_quality 已包含抽帧、TIAS 调度、帧结果聚合与结果写入。
  5. 实例选择应集中在线网关按完整 HTTP 请求查询容量并选择一个实例。
  6. 离线发布需要一致性任务库与 Outbox 同事务，Kafka 发布失败不丢任务。
  7. 资源图必须贴近现实PostgreSQL、Kafka、Redis 独立容器，算法按 GPU 能力稀疏部署。

任务状态与第一版边界

离线任务有课程与节点两级状态；在线图片和实时语音只记录调用与会话指标。

PENDING→ READY→ DISPATCHED→ RUNNING / WAITING_CALLBACK→ SUCCEEDED / FAILED / CANCELLED

四条视图的边界

  • 离线课程平台下载 T/S/P 一次，三条泳道共享课程工作目录，结果落库后清理。
  • PPT 单图每个 ppt_image_id 独立执行 OCR 与 /v1/extract_keywords。
  • 在线图片Base64 请求按完整 HTTP 请求选择实例，不进 Kafka，不跨实例拆图。
  • 实时语音WebSocket 会话开始时选实例，字幕直接返回播放器，默认不入库。
  • 注册部署PostgreSQL、Kafka、Redis 独立容器；容器端点作为注册实例。
