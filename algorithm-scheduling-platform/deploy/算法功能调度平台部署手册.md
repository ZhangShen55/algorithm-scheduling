## 3. Git、镜像和模型准备

目标机的 GitHub Deploy Key 由部署人员预先放在
`/root/.ssh/algorithm-scheduling-github-deploy`，私钥内容不进入 Git、手册、命令参数或报告。目标机的
默认 SSH 身份不能代替该 Deploy Key；clone、fetch 和后续 Git 操作都必须显式选择它：

```bash
set -euo pipefail
export GIT_TERMINAL_PROMPT=0
export DEPLOY_BRANCH=codex/milestone-2b-three-gpu-deployment
export DEPLOY_GIT_SHA='<经批准发布的40位完整SHA>'
export GIT_SSH_COMMAND='ssh -i /root/.ssh/algorithm-scheduling-github-deploy -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes'
export DEPLOY_REPOSITORY='git@github.com:ZhangShen55/algorithm-scheduling.git'

test -f /root/.ssh/algorithm-scheduling-github-deploy
test ! -L /root/.ssh/algorithm-scheduling-github-deploy
test "$(stat -c %a /root/.ssh/algorithm-scheduling-github-deploy)" = 600
test "$(stat -c %u /root/.ssh/algorithm-scheduling-github-deploy)" = "$(id -u)"
test "$(stat -c %h /root/.ssh/algorithm-scheduling-github-deploy)" = 1
install -d -m 0700 /root/workspace
cd /root/workspace
if [ ! -d algorithm-scheduling/.git ]
then
  git clone --branch "$DEPLOY_BRANCH" \
    "$DEPLOY_REPOSITORY" algorithm-scheduling
fi

git_status_before="$(git -C algorithm-scheduling status --porcelain --untracked-files=all)"
test -z "$git_status_before"
test "$(git -C algorithm-scheduling remote get-url origin)" = "$DEPLOY_REPOSITORY"
git -C algorithm-scheduling fetch --depth=1 origin "$DEPLOY_GIT_SHA"
git -C algorithm-scheduling checkout --detach FETCH_HEAD
test "$(git -C algorithm-scheduling rev-parse HEAD)" = "$DEPLOY_GIT_SHA"
git_status_after="$(git -C algorithm-scheduling status --porcelain --untracked-files=all)"
test -z "$git_status_after"

cd /root/workspace/algorithm-scheduling/algorithm-scheduling-platform
export EXPECTED_GIT_SHA="$DEPLOY_GIT_SHA"
```

预期 checkout 处于 detached HEAD，`HEAD` 精确等于经批准的完整 SHA，工作树无修改和
untracked 文件。Deploy Key 缺失、GitHub host key 未受信、fetch 失败、SHA 不存在或工作树
不干净时立即停止；不使用 `reset --hard`、`clean -fd`或删除本地文件来绕过检查。
命令块以 `set -euo pipefail` 失败即停，并同时校验现有 `origin` 与批准仓库完全一致。
密钥必须是当前 UID 所有、`0600`、非符号链接且只有一个硬链接的普通文件。

仓库内的 `deploy/scripts/checkout-release` 是创建“目标目录尚不存在”的原子不可变
checkout 权威入口，并继续由 `DEP-020` 验证。本手册使用约定的固定生产目录，且必须同时
支持已有 clean checkout，因此上述块只负责安全 bootstrap/更新，最终 SHA、工作树与运行时
revision 仍由后续 `preflight` 和发布门禁再次校验。

本里程碑不创建也不读取 `.env`。`.venv` 是平台/Harness Python 环境，不是部署配置。源码就位后再创建
环境并执行宿主机预检：
真实 `OPERATOR_REGISTRY_TOKEN` 是必需的敏感部署输入，必须在登录前由批准的 secret
交付通道注入当前 shell。本手册只验证其已注入，不记录、推导或打印值；不得从运行
容器环境反向提取密钥来补足未授权的交付步骤。


离线单泳道/长课压力前，从 192.168.29.11 对媒体源执行 1/3/10/30 并发下载基线。下列命令
只写 Git 外 `0600` 原始指标，不把媒体写入仓库；`MEDIA_URLS_FILE` 每行是受控 T/S/P URL：

```bash
MEDIA_URLS_FILE=/root/workspace/.algorithm-scheduling-fixtures/media-urls.txt
BASELINE_ROOT=/root/workspace/.algorithm-scheduling-restricted-reports/media-baseline
install -d -m 0700 "$BASELINE_ROOT"
for CONCURRENCY in 1 3 10 30
do
  xargs -P "$CONCURRENCY" -I '{}' curl -fsS -o /dev/null \
    -w '%{url_effective}\t%{size_download}\t%{time_connect}\t%{time_total}\t%{speed_download}\n' \
    '{}' < "$MEDIA_URLS_FILE" > "$BASELINE_ROOT/download-${CONCURRENCY}.tsv"
  chmod 0600 "$BASELINE_ROOT/download-${CONCURRENCY}.tsv"
done
```

同时在源端记录文件服务 CPU/内存/网络，在目标端记录入站网络。每阶梯计算单文件速度、总
吞吐、建连耗时和失败率。若源端/局域网先封顶或持续失败，端到端结果可保留，但不能据此
宣称 GPU 或算子达到最大吞吐。

极限负载运行配置以
[extreme-load-runtime.example.toml](./templates/extreme-load-runtime.example.toml) 为模板，副本必须
位于整个 Git 工作区外、归当前用户所有且权限精确为 `0600`，通过
`ALGORITHM_CAMPAIGN_RUNTIME_CONFIG` 指向，不使用 `.env`。里程碑 2B 的 Kafka lag 权威配置
为 `kafka_probe_timeout_seconds=20.0`、`kafka_probe_attempts=2` 和
`kafka_probe_retry_delay_seconds=0.25`；它是独立 `kafka_lag` 采集面，不与其他探针共享
5 秒超时。其他只读采集面使用 `probe_timeout_seconds=5.0`、`probe_attempts=2` 和
`probe_retry_delay_seconds=0.25`，只允许同一采样内有限重试。全部尝试失败必须锁存 STOP，
并在当前 case 的 `failure_evidence` 中引用脱敏失败事件。

`[fault].semantic_probe_path` 必须指向
`deploy/scripts/extreme-load-fault-probe` 对应的目标机绝对路径。该包装入口固定使用平台
`.venv/bin/python` 运行故障语义探针；虚拟环境或依赖缺失时失败关闭，不依赖目标机全局
Python 临时安装包。

长时间 Campaign 不得使用依附当前 SSH/终端的临时 `while` 循环。先在当前 write-once attempt
目录中选择尚不存在的 PID 和 JSONL 日志路径，再使用正式后台入口；所有 adapter factory 和
case ID 仍原样传给权威 `execute-sequence`：

```bash
deploy/scripts/start-extreme-load-campaign-sequence \
  --pid-file "$ATTEMPT_ROOT/campaign-runner.pid" \
  --log-file "$ATTEMPT_ROOT/campaign-runner.jsonl" -- \
  execute-sequence \
  --plan "$ATTEMPT_ROOT/campaign-plan.json" \
  --release-root "$ATTEMPT_ROOT" \
  --case-id BASE-MEDIA-DOWNLOAD-1 \
  --adapter-factory metrics=scripts.extreme_load.production_adapters:metrics_factory \
  --allow-live-execution
```

入口使用 `nohup` 脱离终端，PID 与日志权限为 `0600`，且已有文件时拒绝覆盖。日志必须先有
`sequence_started`，每案必须成对出现 `case_started`/`case_ended`，最后必须有带退出码的
`sequence_ended`。进程消失、日志缺少逐案终态或 PID 身份不符时，当前 attempt 立即阻断并
保持只读；不得从中断 case 续写。

当前 `192.168.29.12` 只作为媒体源、受控慢响应端点和源端辅助遥测。该主机的 soft
`nofile` 为 1024，且主网卡存在持续增长的 RX drop；在单独完成文件句柄和网卡治理并重新
建立负载机自检证据前，不得用它承载 1000 图片并发或 150 路实时 ASR 权威负载。

tag/digest、预估回收空间及保护集/候选集无交集；把输出摘要作为唯一审核值：

```bash
deploy/scripts/production-image-lifecycle execute \
  --plan "$PLAN" --approved-sha256 "${APPROVED_PLAN_SHA256:?reviewed digest}" \
  --result "$RESULT"
```

执行会二次 inventory；任何容器引用/状态/镜像漂移都在首次删除前失败。删除命令只接受计划
中的完整容器/镜像 ID，并记录删除前摘要、时间、成功/失败、删除后 inspect 和
`docker system df` 前后。任一失败都使阶段不符合，不能改写原 dry-run 掩盖失败。

`docker buildx du` 确认空间仍由可回收 BuildKit 缓存占用。只有取得本次明确授权后，才允许
执行以下固定命令：

```bash
docker buildx prune --all --force --keep-storage 100GB
```

执行前后必须把 `df -B1 /`、`docker system df`、`docker buildx du`、镜像完整 ID 和运行容器
清单写入当前 release 的 `cleanup/`，并验证缓存操作前后镜像集合零减少、当前发布/回滚/基础
镜像、8 个平台/中间件容器、NVIDIA Runtime 和三张 GPU。精确镜像清理结束到缓存操作开始之间
已经存在的外部状态漂移必须单独记录，不能归因于缓存命令。该命令仅清理可重新构建的 BuildKit 缓存；不得替换为
`docker system prune`、`docker image prune`，不得删除容器、卷、模型、Git、`/data/result`
或历史证据。执行后仍低于警戒线时停止构建并重新评审空间方案。

## 7. 首次部署、迁移和常驻启动

权威常驻入口不同于 Canonical 验收控制器：常驻入口不会在验收末尾停止本轮新算子，也不
复用原业务 snapshot/pause/restore 事务。

数据库迁移覆盖 `migrations/0001`–`0007` 及后续连续编号文件。先看只读计划；正式迁移由
常驻启动在 PostgreSQL 健康后自动顺序执行，也可独立调用：
执行写操作前必须先生成并验证当前 PostgreSQL 备份可读；`start-production-stack` 会自动调用
`--adopt-existing`，不能把启动命令当成只读检查。

```bash
deploy/scripts/apply-database-migrations --git-sha "$EXPECTED_GIT_SHA" --plan
deploy/scripts/apply-database-migrations --git-sha "$EXPECTED_GIT_SHA" --adopt-existing
```

首次、重复和中断续跑使用数据库表 `algorithm_schema_migrations` 的文件名、SHA-256 和应用
Git SHA 账本；未知版本、版本间断或已应用文件摘要变化均失败关闭。`--adopt-existing` 对空库
仍按顺序执行全部迁移；非空旧库必须与临时 schema 中的唯一连续 `0001`–`N` 前缀完全一致。
既有 `public.algorithm_schema_migrations` 必须先通过列、类型、默认值、空值性、主键、唯一/检查约束、
索引、表注释、owner/ACL 和访问方法签名；空但结构异常的账本也失败关闭。采纳在 `public` 边界内
对平台表取独占锁，并对 `pg_catalog.pg_class` 取 `SHARE` 锁，阻塞采纳期间新发起的关系对象 DDL。目录锁后
必须确认除当前迁移连接外没有任何未结束事务或 prepared transaction；否则失败并要求先停止旧平台流量、排空事务。
随后迁移器在锁内动态读取每个序列当前 `CACHE` 值并原值重申，只为取得序列关系锁，不使用预扫描旧值，
因此不会覆盖已提交的配置漂移，且会阻塞新的 `ALTER SEQUENCE`/`setval()`。获得账本独占锁后还会
再次核对账本 canonical 签名，并确保每个有归属列的 identity/serial 序列下一值不会与当前表 `MAX/MIN` 键冲突，
且在 `seqmin/seqmax` 范围内、不使用 cycle，序列 `relpersistence` 也必须与前缀迁移一致，再校验表访问方法、表、列、约束、索引、序列、注释、权限、RLS、触发器、策略、
规则和必需数据不变量，然后只写入该前缀账本，剩余版本继续正常迁移。当前目标机是完整 v6，安全路径是
采纳 `0001`–`0006` 后执行 `0007`；任何无唯一前缀、部分结构、异常回填值或漂移都拒绝启动。
锁等待上限为 30 秒；若旧平台仍有任何事务，必须停止四平台旧容器的新流量并排空后重试，不得去掉事务门禁、锁或放宽签名校验。
迁移失败只输出退出码和 stderr SHA-256 摘要，避免把数据库驱动的默认值、注释或行内容写入普通部署日志。

启动完整常驻栈：

```bash
deploy/scripts/start-production-stack \
  --git-sha "$EXPECTED_GIT_SHA" --release-tag "$RELEASE_TAG" \
  --reports-root "$REPORT_ROOT"
```

入口按 PostgreSQL/Kafka/Redis/MongoDB、数据库迁移、四个平台服务、GPU0、GPU1、GPU2、
CPU profile 顺序启动；每个 profile 完成立即校验 image revision、运行包、注册和首次心跳，
最后要求完整 21/21。成功后以 `0600` 原子写 `PRODUCTION_LEDGER` 指向的 29 容器权威账本。
任一步失败保留现场并返回非零；先查询状态/日志，不能改用宽泛 Compose 操作跳过。

## 9. 升级、回滚和验收后退役

### 9.1 同 SHA 续跑和新 SHA 升级

同 SHA 续跑先执行 `status-production-stack`；健康则不重建。新 SHA 升级依次执行：旧栈
inventory/保护基线、构建前 dry-run、模型校验、11 镜像构建/attestation、迁移计划、常驻
启动、21/21/7/7 Smoke、Campaign 和原有 217+26+6 门禁。任一新版本门禁失败都保留旧版
容器和镜像，不允许验收后退役。
因此 11.7 的同 SHA 独立复现在 `status=PASS` 时引用已有 `production-stack.json`
作为常驻启动账本，不重复调用 `start-production-stack`；只在栈未建立或状态不健康且
已取得真实 registry token 时，才按第 7 节启动或精确恢复。

### 9.2 回滚

停止新负载并等待已接受任务/租约受控排空；使用旧 Git SHA、旧配置、外部模型 manifest 和
旧 11 镜像重新调用权威常驻入口。数据库迁移是只前进合同，回滚前须确认旧程序兼容当前
schema；不通过删除数据库卷回滚。旧镜像若已在最终退役阶段删除，则按记录的 Git SHA、
Dockerfile、基础镜像和外部 manifest 重建，历史 release 证据保持只读。

### 9.3 验收后精确退役

只有新版同 SHA 的必需预检、11 镜像、四平台、21 实例、Campaign、217 条反例、26 条压力/
恢复、6 项 B 级复核全部符合，才可建立 `postacceptance` 计划。先停止并审核每个旧容器，按
完整 ID 传 `--retire-container-id`，同时逐项传入与该 ID 审核结果一致的
`--retire-compose-identity <compose_project>/<compose_service>`，并传
`--acceptance-status PASS`；流程先保存其 Compose、
状态、镜像 digest/release 和删除前摘要，再删旧容器、重算镜像候选并删旧镜像。

执行结果只能是 `AWAITING_REVALIDATION`，不能直接宣布清理完成。重新运行
`status-production-stack` 和 7/7 算子 Smoke 后，用实际证据发布最终结论：

```bash
deploy/scripts/production-image-lifecycle verify \
  --result "$RESULT" --stack-status "$STATUS_JSON" \
  --smoke-evidence "$RELEASE_ROOT/smoke/asr_offline.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/asr_online.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/facerec.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/ocr.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/ppt_slice.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/screen_det.json" \
  --smoke-evidence "$RELEASE_ROOT/smoke/vbas.json" \
  --output "$RELEASE_ROOT/cleanup/cleanup-completion.json"
```

任一中间件/平台/实例、GPU 归属、注册/租约或 Smoke 不就绪时，不发布清理完成结论。

## 11. 常见故障排查

| 现象 | 只读查询 | 判定依据 | 受控处置 | 禁止操作 |
|---|---|---|---|---|
| 算子未注册 | `status-production-stack`、`/ops/operator-instances`、容器日志 | 缺实例、非 ONLINE、`model_ready=false` | 检查 token/config/网络，精确重启该实例并等首次心跳 | 删除 Redis key 伪造恢复 |
| 租约不释放 | `/ops/operator-instances/snapshot`、实例 active-leases | `active_lease_count` 持续非零且工作已终态 | 停止新流量，查调用方/TTL，精确恢复相关服务 | 手工写 Redis 租约 |
| Kafka lag 不下降 | `/ops/queues`、Kafka consumer group、Orchestrator 日志 | Outbox/lag 持续增长 | 验证 `kafka:29092` 和 consumer，精确重启 Orchestrator | 清空 Kafka/PostgreSQL |
| GPU 不可见/跨卡 | `docker inspect`、`nvidia-smi` | DeviceRequests、UUID、PID 与 gpu0/1/2 不符 | 停止新负载，精确重建该 profile | 修改容器名掩盖跨卡 |
| 日志不生成 | 容器 stdout、实例日志目录权限 | handler/目录不可写或实例目录冲突 | 修复精确实例目录权限后重启实例 | 记录媒体/凭据定位 |
| 共享目录不可写 | `test -w`、mount inspect、`/ops/storage` | 容器与宿主路径不一致 | 修复明确 bind/UID，先保留结果 | 删除 `/data/result` |
| 镜像清理漂移 | inventory、dry-run、Docker inspect | 新容器引用候选或摘要变化 | 放弃旧计划，重新 inventory/审核 | 宽泛 prune 或强制删镜像 |
