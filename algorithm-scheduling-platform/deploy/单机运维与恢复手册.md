# 算法调度平台单机运维与恢复手册

## 1. 适用范围与数据分级

本文适用于第一阶段的单机 Docker 部署：四个平台服务、全部算法实例、PostgreSQL、Kafka、Redis、MongoDB 位于同一台服务器，并共享 `/data/course` 和 `/data/result`。

## 0. 里程碑 2B 验证前提

目标服务器地址为 `root@192.168.29.11:22`，代码目录为
`/root/workspace/algorithm-scheduling`，登录密码为 `kedacom_123`。服务器必须为 x86_64，具有三张 NVIDIA
GPU、Docker/NVIDIA Container Runtime，且 `/data/course`、`/data/result` 可写；
PostgreSQL、Redis、Kafka、MongoDB 均须可用。本次部署不使用 `.env`；用户已批准 Git
保存部署模板、该登录合同和受控服务默认值。上述服务器密码是批准例外；Deploy Key/私钥、
模型解密密钥、课程/人脸媒体、大型 fixture 和外部可信模型 manifest 仍通过外部安全通道
提供，不得进入 Git、普通报告、镜像上下文或命令参数。

部署前执行 `harness/scenarios/milestone-2b-deploy.md` 的 `preflight`、快照和
暂停步骤。不得宽泛暂停预存业务；同一账本中只暂停用户明确允许的原 `ocr-v6-amd`，并在
只停止本轮 ledger 记录的新增算子后恢复。新增算子不在本流程中执行 `docker rm`；
baseline/current/new ledger 的原子发布与复核以 canonical scenario 为准。canonical 2B 场景不对
platform/infrastructure 执行 `down` 或
`stop`；禁止 `docker system prune`、`docker compose down -v`、删除卷和删除 `/data/result`。

| 数据 | 位置 | 重要性 | 恢复方式 |
|---|---|---:|---|
| 课程、任务、节点、结构化结果、Outbox | PostgreSQL | 最高 | 数据库备份恢复 |
| PPT 切片、精选视觉证据 | `/data/result/{task_id}` | 最高 | 文件备份恢复 |
| 下载视频、WAV、普通抽帧 | `/data/course/{task_id}` | 临时 | 可从 A 提供的 URL 重新下载 |
| 算子注册、心跳、容量租约 | Redis | 可重建运行态 | 算子重新注册和心跳；租约等待 TTL 到期 |
| 课程触发和视觉命令/事件 | Kafka | 可恢复传输态 | 重启消费者；未发布事件由 Outbox 补发 |
| 人脸 embedding 和人物数据 | MongoDB | 领域数据 | MongoDB 备份恢复 |

PostgreSQL 与 `/data/result` 必须成组备份。不能把 Kafka 或 Redis 当作任务状态和业务结果的唯一来源。

## 2. 日常检查

### 2.1 基础设施

在 `algorithm-scheduling-platform` 目录执行：

```bash
docker compose -f deploy/docker-compose.platform.yml ps
docker compose -f deploy/docker-compose.platform.yml logs --tail=200 postgres kafka redis mongodb
```

四个基础设施容器应为 `running` 或 `healthy`。主机方式运行平台进程时，连接地址为 `127.0.0.1:5432`、`127.0.0.1:9092`、`127.0.0.1:6379`、`127.0.0.1:27017`；MongoDB 使用 `authSource=admin`。Kafka 固定监听 `EXTERNAL://:9092`、`INTERNAL://:29092`，分别广播 `EXTERNAL://127.0.0.1:9092`、`INTERNAL://kafka:29092`。

对 A/远程可信内网只开放 `18100` 和 `18103`。`5432`、`9092`、`6379`、`27017`、
`18101`、`18102` 和全部算子宿主机端口必须只绑定 `127.0.0.1`；容器间仍用服务名。

### 2.2 平台和队列

```bash
curl -fsS http://127.0.0.1:18100/health
curl -fsS http://127.0.0.1:18100/ops/queues
curl -fsS http://127.0.0.1:18100/ops/operator-instances
curl -fsS http://127.0.0.1:18100/ops/storage
curl -fsS http://127.0.0.1:18100/metrics
```

运维接口使用真实 HTTP 状态码：资源不存在为 `404`，依赖不可用为 `503`。A 服务使用的 `/api/course-jobs` 接口仍然是 HTTP 200 加业务码，两者不能混为一套告警规则。

检查单节课及其所有业务管道和节点：

```bash
curl -fsS http://127.0.0.1:18100/ops/course-jobs/course-001
```

重点关注：

- `status=30`：等待算子，结合实例列表检查 capability、`model_ready` 和 lifecycle。
- `outbox_pending` 持续增长：检查 orchestrator 内的 Outbox Publisher 和 Kafka。
- `/data/course` 持续增长：检查任务是否达到终态、长期结果是否成功写入。
- 实例为 `DRAINING` 或 `OFFLINE`：不会接收新请求。

## 3. 备份

### 3.1 PostgreSQL 逻辑备份

先创建权限受控的备份目录，然后执行：

```bash
docker compose -f deploy/docker-compose.infrastructure.yml exec -T postgres \
  pg_dump -U algorithm -d algorithm -Fc > /srv/algorithm-backup/algorithm-20260805.dump
```

使用临时数据库验证备份可读取：

```bash
docker compose -f deploy/docker-compose.infrastructure.yml exec -T postgres \
  pg_restore -l < /srv/algorithm-backup/algorithm-20260805.dump
```

### 3.2 长期结果文件备份

在数据库备份相同的维护窗口，对结果目录做快照或归档：

```bash
tar -C /data/result -czf /srv/algorithm-backup/result-20260805.tar.gz .
```

生产环境优先使用文件系统快照或增量备份。备份应记录数据库 dump 与结果快照的共同批次号和时间，恢复时必须使用同一批次。

### 3.3 Kafka 与 Redis

Kafka 和 Redis Docker volume 可用于缩短原机恢复时间，但不是业务备份替代品：

- Kafka 丢失后，尚未发布的数据库 Outbox 会补发；已经发布但尚未完成的节点由数据库状态和恢复流程重新发现。
- Redis 丢失后，算子会重新注册；旧租约不应人工伪造，等待 TTL 或由进程重启清除。

## 4. 有序重启

### 4.1 重启顺序

1. PostgreSQL、Kafka、Redis、MongoDB。
2. 执行数据库迁移检查和迁移。
3. `control-service`。
4. 算子容器，使实例重新注册。
5. `orchestrator-service` 和 `vision-orchestrator-service`。
6. `online-gateway-service`。
7. 检查 Outbox、队列、实例和抽样课程状态。

基础设施启动命令（仅在报告 release/SHA 已初始化后）：

```bash
EXPECTED_GIT_SHA="$(git -C .. rev-parse HEAD)"
EXPECTED_GIT_SHA="$EXPECTED_GIT_SHA" \
  docker compose -f deploy/docker-compose.platform.yml up -d --build --wait --wait-timeout "${PLATFORM_WAIT_TIMEOUT_SECONDS:-180}"
docker compose -f deploy/docker-compose.platform.yml ps
deploy/scripts/preflight runtime --git-sha "$EXPECTED_GIT_SHA"
```

当前平台进程以主机方式运行时，分别进入四个服务根目录执行：

```bash
python -m uvicorn app.main:app --host 0.0.0.0 --port 18100 --workers 1  # control_service
python -m uvicorn app.main:app --host 127.0.0.1 --port 18101 --workers 1  # orchestrator_service
python -m uvicorn app.main:app --host 127.0.0.1 --port 8010 --workers 1   # vision_orchestrator_service
python -m uvicorn app.main:app --host 0.0.0.0 --port 18103 --workers 1  # online_gateway_service
```

生产环境应由 systemd、Supervisor 或 Docker Compose 管理这些进程，不应依赖人工长期占用终端。

算子启动必须使用
`harness/scenarios/milestone-2b-deploy.md` 阶段 3 定义的 canonical
`start_operator_profile`。必须从发布变量开始，在同一 Bash 会话中依次执行阶段 1/2 后
进入阶段 3，不得单独加载阶段 3，也不得直接调用算子 Compose `up`；下列循环只说明
helper 与 preflight 的顺序：

首次发布保持 `PREVIOUS_RELEASE_ROOT` 为空。同 release tag 换 SHA 续跑时，显式指向
上一 SHA 的绝对 release 目录。canonical 场景会在 snapshot/pause 前获取 tag 级
非阻塞锁；锁以 `O_NOFOLLOW` 安全打开，并持有到阶段 6 恢复成功后才释放。
锁冲突或锁文件的 UID/权限/类型不安全时不得继续 Compose。

```bash
docker network inspect algorithm-platform >/dev/null 2>&1 || docker network create algorithm-platform
for profile in gpu0 gpu1 gpu2 cpu
do
  start_operator_profile "$profile"
  deploy/scripts/preflight operators --profile "$profile" \
    --git-sha "$EXPECTED_GIT_SHA" \
    --control-url http://127.0.0.1:18100 \
    --release-tag v1.0_260812 --reports-root "$PWD/deploy/reports"
done
deploy/scripts/preflight operators --full --git-sha "$EXPECTED_GIT_SHA" \
  --control-url http://127.0.0.1:18100 \
  --release-tag v1.0_260812 --reports-root "$PWD/deploy/reports"
docker compose -f deploy/docker-compose.operators.yml ps
```

里程碑 2B 的逐卡启动、模型清单、镜像构建、GPU/注册/Smoke 和报告命令以
`harness/scenarios/milestone-2b-deploy.md` 为准；本手册不复制另一套可能漂移的参数。
其中外部 `model-assets.manifest.json` 是可信交付基线，部署只执行 stage/verify，不重新
生成；平台和算子最终镜像都必须与 `EXPECTED_GIT_SHA` 一致。Smoke 报告中的 SHA 不是
镜像 attestation。

same SHA 已有完整 snapshot/paused 时直接复用。previous release 续跑从其
直接账本或 provenance 取得原 authority；A→B→C 中 C 的指针记录 B 为
立即前驱，但 snapshot/paused 仍指向 A。当前 release 只以不可替换方式保存
当前 UID 所有的 `0400` provenance，不重新快照、暂停或复制 paused ledger。
fresh host preflight 不授权任何已占用端口；续跑只授权经 platform/operator Compose
配置、running 状态、project/service 标签和实际端口映射共同证明的精确
“监听地址+端口”端点。同端口的其他地址或地址族监听仍被拒绝。
算子 baseline/new 也必须
成对且排序、ID、inspect 和 Compose 身份有效。新 SHA 只在
`current - previous baseline == previous new` 精确成立时继承 baseline，然后立即刷新
new；同 SHA 恢复保留 baseline，partial ledger 则 fail closed。Compose 换 ID 后通过刷新 new
记录当前 ID，不删除容器绕过校验。

### 4.2 重启后的核验

```bash
curl -fsS http://127.0.0.1:18100/ops/operator-instances
curl -fsS http://127.0.0.1:18100/ops/queues
curl -fsS http://127.0.0.1:18100/ops/storage
```

确认所有计划中的实例已出现、`model_ready=true`、生命周期为 `ONLINE`；Outbox 积压应逐步下降，等待算子的节点应在对应 capability 恢复后重新进入调度。

## 5. 算子排空、维护和恢复上线

先通过 control-service 将实例排空：

```bash
curl -fsS -X POST http://127.0.0.1:18100/ops/operator-instances/ocr-gpu0/drain
curl -fsS http://127.0.0.1:18100/ops/operator-instances
```

进入 `DRAINING` 后不再分配新任务，现有请求允许完成。确认 `inflight=0` 后，再停止、升级或重启对应容器。禁止直接删除 Redis 注册键来模拟排空。

实例重启后，注册客户端先重新注册为 `OFFLINE`，再立即发送首次心跳；只有该心跳成功且模型 ready 后才成为 `ONLINE` 路由候选。后续心跳遇到短暂 HTTP 故障会按周期重试。若不重启，需要调用平台生命周期接口显式恢复；恢复前必须确认模型已经 ready。同一 `instance_id` 不得同时用于两个存活容器。

## 6. 磁盘清理

### 6.1 自动清理边界

只有同时满足以下条件，平台才可清理 `/data/course/{task_id}`：

1. 本次请求的全部任务类型已达到 `60/70/80` 终态。
2. 全部节点已达到终态。
3. 声明的长期文件已实际存在于 `/data/result/{task_id}`。
4. 清理目标经过校验，确实位于配置的 course 根目录内。

`/data/result/{task_id}` 不属于终态清理范围。PPT 切片和精选视觉证据需要按业务保留策略另行归档。

### 6.2 人工清理流程

先查容量与大目录：

```bash
curl -fsS http://127.0.0.1:18100/ops/storage
du -sh /data/course/* /data/result/* 2>/dev/null | sort -h
```

再通过 `/ops/course-jobs/{task_id}` 确认具体课程全部请求管道和节点终态，并核对 `/data/result/{task_id}` 中的长期文件。人工处理优先移动到隔离目录，保留回滚窗口：

```bash
mkdir -p /data/quarantine
mv /data/course/course-001 /data/quarantine/course-001-20260805
```

不得对 `/data/course`、`/data/result`、工作区根目录使用宽泛递归删除；不得使用未校验变量、通配符或空 task_id 作为删除目标。

## 7. 单机故障恢复

### 7.1 control-service 故障

- A 暂时不能提交/查询，算子心跳和新租约也会失败。
- 已在算子执行中的请求可结束，但新工作不应继续分配。
- 重启 control-service，检查 PostgreSQL 与 Redis，再确认实例重新心跳。

### 7.2 orchestrator-service 故障

- 已提交任务及 Outbox 仍保存在 PostgreSQL。
- 重启后 Publisher 扫描未发布 Outbox，Consumer 依靠幂等键避免重复初始化。
- 检查 `outbox_pending` 是否下降，并抽查运行中课程节点。

### 7.3 Kafka 故障

- control-service 仍可事务性接收任务，Outbox 保留待发事件。
- 恢复 Kafka 后重启或等待 Publisher 重连；不能手工把任务标为完成。
- 通过 `/ops/queues` 观察 Outbox 积压下降。

### 7.4 Redis 故障

- 停止新的容量路由；内部接口应返回 `503`，不能绕过租约直接调用任意实例。
- 恢复 Redis 后让算子重新注册/心跳，检查实例列表。
- 旧租约依靠 TTL 回收；若 Redis 数据完全丢失，确认没有仍在执行的旧请求后再恢复入口流量。

### 7.5 PostgreSQL 故障或数据损坏

1. 停止 A 流量、orchestrator、vision orchestrator 和 online gateway 的离线相关入口。
2. 保留故障数据库卷，不在原卷上反复覆盖恢复。
3. 建立新的 PostgreSQL 实例并恢复同批次数据库 dump。
4. 恢复同批次 `/data/result` 快照。
5. 运行迁移检查，启动 control-service，再按有序重启流程恢复其余服务。
6. 检查 Outbox、节点状态和长期文件；对执行中断节点按后续明确的恢复/补跑规则处理，不能直接伪造完成状态。

数据库恢复示例应在新的空数据库上执行：

```bash
docker compose -f deploy/docker-compose.infrastructure.yml exec -T postgres \
  pg_restore -U algorithm -d algorithm --clean --if-exists \
  < /srv/algorithm-backup/algorithm-20260805.dump
```

### 7.6 算子实例故障

- Docker 的 `restart: unless-stopped` 负责进程拉起。
- 心跳过期的实例从路由候选中排除；同能力其他实例可继续接收请求。
- 若无同能力实例，离线节点保持 `status=30` 并显示中文原因；在线请求返回容量不可用，不进入 Kafka。

## 8. 恢复完成判定

以下条件全部满足后才恢复 A 的正常流量：

- PostgreSQL、Kafka、Redis、MongoDB 健康。
- 四个平台服务 `/health` 可用。
- 计划中的算子全部注册，模型 ready，非计划维护实例之外均为 `ONLINE`。
- Outbox 积压不再增长并能够下降。
- `URGENT`/`NORMAL` 队列继续流动，无异常长期停留的运行节点。
- 抽查一节已完成课程，结构化结果和 `/data/result/{task_id}` 文件一致。
- 在线图片请求不进入 Kafka，实时 ASR 会话可建立并在断开时释放容量。

每次恢复应记录故障时间、受影响 task_id、执行命令、备份批次、恢复验证结果和负责人。
