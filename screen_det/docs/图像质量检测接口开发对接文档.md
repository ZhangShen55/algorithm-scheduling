# 屏幕检测服务北向接口开发对接文档

## 1. 文档说明

本文档面向北向业务系统开发与联调人员，只定义以下两个接口：

| 接口 | 方法 | 路径 | 用途 |
|------|------|------|------|
| 健康检查 | GET | `/health` | 判断服务及两个YOLO模型是否已就绪 |
| 全量检测 | POST | `/detect_all` | 单张图片一次完成倾斜、幕布、画质异常和镜头遮挡检测 |

## 2. 通用约定

### 2.1 服务地址

```text
http://10.80.5.130:8880
```

默认端口为`8880`，实际地址以部署环境提供的信息为准。

### 2.2 数据格式

- 字符编码：UTF-8。
- `/detect_all`请求和响应均使用JSON。
- `/detect_all`请求必须设置`Content-Type: application/json`。
- 数值耗时字段的单位均为毫秒。
- 时间字段`start_time`、`end_time`为Unix毫秒时间戳字符串。
- 当前服务本身未定义鉴权请求头；如果部署在网关后，应按网关要求增加鉴权信息。

### 2.3 请求标识

调用方可以通过`X-Request-ID`请求头传递请求标识。服务会在响应头中返回同名标识；未传时由服务自动生成。

```http
X-Request-ID: north-system-20260720-000001
```

建议调用方记录该响应头，便于跨系统日志定位。

## 3. 健康检查

### 3.1 请求

```http
GET /health
```

无请求参数和请求体。

### 3.2 HTTP状态

| HTTP状态 | 含义 |
|----------|------|
| 200 | 服务已就绪，两个模型均已加载并完成预热 |
| 503 | 服务未就绪，至少一个模型未完成加载或预热 |

北向系统只有在HTTP状态为200且`ready=true`时，才能向实例发送检测请求。

### 3.3 响应字段

| 字段 | 类型 | 说明 |
|------|------|------|
| status | string | `success`表示就绪，`not_ready`表示未就绪 |
| ready | boolean | 是否可以接收检测流量 |
| elapsed_time | string | 服务运行时长，格式为`<小时>h <分钟>m <秒>s` |
| total_requests | integer | 服务累计处理的业务请求数 |
| memory_mb | number | 当前服务进程内存占用，单位MB |
| yolo | object | 设备配置和实际解析结果 |
| screen_model | object | 幕布检测模型状态 |
| occlusion_model | object | 遮挡分割模型状态 |

`yolo`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| device | string | 配置模型的设备，例如`cpu`、`cuda:0` |
| tilt_inference_device | string | 倾斜检测执行设备，当前固定为`cpu` |
| yolo_device_resolved | string | 模型实际解析使用的设备 |
| cuda_visible_devices | string/null | 进程读取到的`CUDA_VISIBLE_DEVICES`环境变量 |

`screen_model`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| loaded | boolean | 模型是否已加载到内存 |
| warmed_up | boolean | 模型是否已完成预热推理 |
| device | string/null | 模型实际推理设备；尚未加载时可能为`null` |
| device_name | string/null | CUDA设备名称；CPU模式为`null` |
| gpu_memory_mb | number/null | 模型预热后的GPU显存占用；CPU模式为`null` |
| aattn_patched | integer | 模型兼容补丁处理的层数，仅用于运行状态诊断 |

`occlusion_model`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| loaded | boolean | 模型是否已加载到内存 |
| warmed_up | boolean | 模型是否已完成预热推理 |
| device | string | 模型实际推理设备 |

## 4. 全量检测

### 4.1 请求

```http
POST /detect_all
Content-Type: application/json
```

单次请求只接受一张图片。

### 4.2 请求字段

| 字段 | 必填 | 类型 | 约束 | 默认值 | 说明 |
|------|------|------|------|--------|------|
| image | 是 | string | 非空Base64 | 无 | 单张图片内容 |
| tilt_threshold | 否 | number | 大于等于0 | 1.5 | 倾斜判定阈值，单位度 |
| screen_conf | 否 | number | 0到1 | 0.25 | 幕布模型置信度阈值 |
| screen_iou | 否 | number | 0到1 | 0.45 | 幕布 NMS IoU阈值 |
| occlusion_threshold | 否 | number | 0到1 | 0.25 | 遮挡分割模型置信度阈值 |
| occlusion_area_ratio | 否 | number | 0到1 | 0.2 | 遮挡面积占整张画面的判定阈值 |
| include | 否 | string[] | 见模块枚举 | 全部模块 | 指定本次执行的检测模块 |

表中的默认值为当前默认配置。服务最终实际使用值始终以响应中的`effective_params`为准。

`include`模块枚举：

| 值 | 说明 |
|----|------|
| tilt | 画面倾斜检测 |
| screen | 蓝、黑、白、正常幕布检测 |
| quality_abnormal | 虚焦、偏色、雪花噪点、花屏检测 |
| occlusion | 镜头前或镜头不远处遮挡检测 |

`include`不传时执行全部四个模块。重复模块会按首次出现的顺序去重。传入空数组`[]`表示不执行任何模块，不会使用默认模块。未执行模块对应的响应结果块为`null`。

### 4.3 图片Base64要求

- 支持纯Base64字符串。
- 支持`data:image/jpeg;base64,`、`data:image/png;base64,`等data URL前缀。
- Base64中的空格和换行会被忽略。
- 解码后必须是OpenCV可以识别的有效图片。
- 当前默认允许的解码后图片大小上限为10MB，实际限制由服务配置决定。
- 推荐调用方在发送前去除不必要的换行，避免增加请求体积和日志排查难度。

### 4.4 最简请求示例

```json
{
  "image": "<IMAGE_BASE64>"
}
```

### 4.5 覆盖参数请求示例

```json
{
  "image": "<IMAGE_BASE64>",
  "tilt_threshold": 1.5,
  "screen_conf": 0.25,
  "screen_iou": 0.45,
  "occlusion_threshold": 0.25,
  "occlusion_area_ratio": 0.2,
  "include": [
    "tilt",
    "screen",
    "quality_abnormal",
    "occlusion"
  ]
}
```

### 4.6 顶层响应字段

| 字段 | 类型 | 说明 |
|------|------|------|
| code | integer | 请求执行状态，成功进入检测流程时为200 |
| msg | string | `检测完成`或`检测完成，部分模块失败` |
| start_time | string | 服务开始处理时间，Unix毫秒时间戳字符串 |
| end_time | string | 服务完成处理时间，Unix毫秒时间戳字符串 |
| cost_ms | number | 聚合检测总耗时 |
| executed_modules | string[] | 本次实际执行的模块 |
| failed_modules | string[] | 发生技术执行失败的模块 |
| effective_params | object | 本次实际生效的参数和设备 |
| problem_types | string[] | 检测出业务问题的模块 |
| tilt | object/null | 倾斜检测结果；未执行时为`null` |
| screen | object/null | 幕布检测结果；未执行时为`null` |
| quality_abnormal | object/null | 画质异常结果；未执行时为`null` |
| occlusion | object/null | 遮挡检测结果；未执行时为`null` |

`effective_params`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| tilt_threshold | number | 实际使用的倾斜阈值 |
| screen_conf | number | 实际使用的幕布置信度阈值 |
| screen_iou | number | 实际使用的幕布NMS IoU阈值 |
| occlusion_threshold | number | 实际使用的遮挡置信度阈值 |
| occlusion_area_ratio | number | 实际使用的遮挡面积阈值 |
| include | string[] | 实际执行模块 |
| device | string | 两个YOLO模型统一使用的推理设备 |

### 4.7 业务问题判定

`problem_types`是北向系统获取检测结论的首要字段，枚举如下：

| 值 | 进入数组的条件 |
|----|----------------|
| tilt | `tilt.result.is_tilted=true` |
| screen | 未检测到有效幕布，或者幕布主类别为蓝、黑、白 |
| quality_abnormal | `quality_abnormal.is_abnormal=true` |
| occlusion | `occlusion.is_occluded=true` |

示例：

```json
{
  "problem_types": [
    "tilt",
    "occlusion"
  ]
}
```

表示画面存在倾斜和镜头遮挡问题。

不能仅凭`problem_types`为空就认定全部正常。北向系统还必须确认：

1. 期望模块均出现在`executed_modules`中。
2. `failed_modules`为空。
3. 再根据`problem_types`判断业务异常。

### 4.8 幕布类别枚举

`screen.primary`表示置信度最高的幕布结果，`screen.detections`表示全部有效检测框。

| label | 类别 | 是否计入`screen`问题 |
|-------|------|----------------------|
| 0 | 蓝幕 | 是 |
| 1 | 黑幕 | 是 |
| 2 | 白幕 | 是 |
| 3 | 正常画面 | 否 |

检测框字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| label | integer | 幕布类别枚举 |
| confidence | number | 模型返回置信度，范围0到1 |
| box | number[4] | 检测框坐标`[x1, y1, x2, y2]`，以原图左上角为原点 |

未检测到有效幕布时`primary=null`，并计入`problem_types`的`screen`问题。

### 4.9 画质异常枚举

一张图片可以同时存在多种画质异常，因此`abnormal_types`是整数数组。

| type | 异常类型 |
|------|----------|
| 1 | 虚焦 |
| 2 | 偏色 |
| 3 | 雪花噪点 |
| 4 | 花屏 |

`quality_abnormal.results`只返回实际命中的异常项：

| 字段 | 类型 | 说明 |
|------|------|------|
| type | integer | 画质异常枚举 |
| score | number | 异常分数，范围0到1，越大表示异常特征越明显 |
| message | string | 单项异常中文提示 |

### 4.10 各模块响应字段

`tilt`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| code | integer | 模块执行状态 |
| msg | string | 模块执行描述 |
| cost_ms | number | 模块耗时 |
| result | object/null | 倾斜结果 |
| result.is_tilted | boolean | 是否超过倾斜阈值 |
| result.angle | number | 检测角度，单位度 |
| result.cost_ms | number | 倾斜检测耗时 |

`screen`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| code | integer | 模块执行状态 |
| msg | string | 模块执行描述 |
| cost_ms | number | 模块耗时 |
| primary | object/null | 置信度最高的检测框 |
| detections | object[] | 全部有效检测框 |

`quality_abnormal`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| code | integer | 模块执行状态 |
| msg | string | 模块执行描述 |
| cost_ms | number | 模块耗时 |
| is_abnormal | boolean | 是否存在任一画质异常 |
| abnormal_types | integer[] | 命中的画质异常枚举 |
| results | object[] | 命中的画质异常明细 |
| message | string | 画质检测总体提示 |

`occlusion`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| code | integer | 模块执行状态 |
| msg | string | 模块执行描述 |
| cost_ms | number | 模块耗时 |
| is_occluded | boolean | 是否判定为镜头遮挡 |
| occlusion_area_ratio | number | 遮挡区域占整张画面的比例，范围0到1 |
| score | number | 遮挡分割结果最高置信度，范围0到1 |
| threshold | number | 本次实际使用的置信度阈值 |
| area_ratio | number | 本次实际使用的遮挡面积判定阈值 |
| message | string | 遮挡检测中文提示 |

### 4.12 子模块失败说明

单个检测模块执行失败时，其他模块继续执行：

- HTTP状态仍可能为200。
- 顶层`code`仍为200。
- `msg`为`检测完成，部分模块失败`。
- 失败模块进入`failed_modules`。
- 失败模块结果块只保证返回`code`、`msg`和`cost_ms`。
- 失败模块不会进入`problem_types`。

示例：

```json
{
  "code": 200,
  "msg": "检测完成，部分模块失败",
  "executed_modules": [
    "tilt",
    "screen",
    "quality_abnormal",
    "occlusion"
  ],
  "failed_modules": [
    "screen"
  ],
  "problem_types": [],
  "screen": {
    "code": 500,
    "msg": "Detection failed: screen inference failed",
    "cost_ms": 2.1
  }
}
```

该示例只展示与失败判定有关的字段，实际响应仍包含其他顶层字段和模块结果。

### 4.13 HTTP错误响应

检测请求未进入正常聚合流程时，返回统一错误结构：

```json
{
  "code": 400,
  "msg": "Missing field \"image\""
}
```

| HTTP状态 | code | 常见原因 | 北向处理建议 |
|----------|------|----------|--------------|
| 400 | 400 | Content-Type错误、缺少image、Base64无效、参数越界 | 修正请求，不要直接重试 |
| 500 | 500 | 聚合检测入口发生未预期异常 | 记录`X-Request-ID`并按策略有限重试 |
| 503 | 503 | 聚合检测接口未启用 | 停止向该实例发流量并告警 |

503示例：

```json
{
  "code": 503,
  "msg": "聚合检测接口未启用"
}
```

### 4.14 调用示例

先生成请求文件`request.json`，其中`image`替换为真实图片Base64，然后调用：

```bash
curl --request POST \
  --url "http://<host>:8880/detect_all" \
  --header "Content-Type: application/json" \
  --header "X-Request-ID: north-detect-000001" \
  --data-binary @request.json
```
