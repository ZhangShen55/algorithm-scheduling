# 算法调度运维控制台前后端对接清单

## 目标与边界

第一阶段是只读观测控制台。前端不调用 A 服务接口，不调用 Control Service 的注册、心跳、生命周期、租约申请/释放或排空写接口，也不直接连接 PostgreSQL、Redis、Kafka、Docker。

前端工程位于 `algorithm-scheduling-ops-console/`。本阶段作为内部工具，生产环境由独立静态容器提供页面，浏览器直接访问配置的 Control Service、online-gateway-service 和 GPU exporter；三个只读服务通过宽松 CORS/OPTIONS 支持跨域。Nginx/BFF 可作为后续统一入口，但不是当前部署前置条件。

## 前端可配置项

当前页面增加“连接与观测配置”抽屉。它是浏览器本地配置，不是平台运行配置，不会影响 A 服务的业务对接：

| 配置项 | 默认值 | 范围/示例 | 作用 | 是否建议开放 |
| --- | --- | --- | --- | --- |
| Control Service 地址 | `http://<页面IP>:18100` | `http://192.168.29.11:18100` | 读取实例、容量、队列、任务、存储和就绪状态 | 是 |
| gateway-online 地址 | `http://<页面IP>:18103` | `http://192.168.29.11:18103` | 读取网关 `/metrics` | 是 |
| GPU 指标容器地址 | `http://<页面IP>:9400` | `http://IP:端口` | 读取整机 GPU `/gpu` 快照 | 是 |
| 总览刷新周期 | `10` 秒 | `5～60` 秒 | 控制总览、实例列表、队列和系统状态轮询 | 是 |
| 实例任务刷新周期 | `5` 秒 | `3～30` 秒 | 控制实例详情 `active-leases` 轮询，观察 task_id/work_type 归属 | 是 |
| 自动刷新开关 | 开启 | 页面顶部已有 | 暂停或恢复轮询 | 是 |
| 界面风格 | `industrial` | 日间模式 / 深色模式 | 当前浏览器显示偏好 | 是 |

配置保存在浏览器 `localStorage`，不同浏览器或不同运维终端互不影响。“测试读取”仅执行只读 GET 请求。默认使用 `/control` 和 `/gateway` 代理路径；直连 IP/端口时需要 Control Service、online-gateway-service 和 GPU exporter 配置 CORS。前端会将刷新周期限制在上述范围，避免误设成高频请求。

## 不建议开放的参数

第一阶段不要把下面参数放到页面表单中：PostgreSQL DSN、Redis 地址/DB、Kafka 地址、算子声明容量、租约 TTL、心跳周期、HTTP 连接池、调度重试次数、队列优先级、启用任务类型、`course_root`/`result_root`、模型路径、容器名称、Compose 项目和 Docker 参数。

这些参数分别影响基础设施连接、容量调度安全、数据路径或部署控制。在线修改需要配置中心或受限运维 API，并配套 RBAC、审计、变更校验、版本化发布、幂等、回滚和操作确认；本阶段只读控制台不承担这类职责。

## 任务追踪分页与排序

当前接口 `GET /ops/course-jobs/{task_id}` 返回一个课程任务详情，前端将其中的 `tasks[]` 渲染为任务类型分栏。页面支持在当前 `task_id` 内选择每页 4/8/12/20 个任务类型，并按平台流程顺序、任务类型、状态或最近更新时间排序，同时支持升序/降序切换。分页和排序在浏览器内完成，不增加后端请求，也不影响 A 服务。

这里的分页对象是单个 `task_id` 内的 `tasks[]`，不是跨 Task ID 的任务列表。若后续需要按时间、状态、任务类型检索全部课程任务，应新增类似 `GET /ops/course-jobs?page=1&page_size=20&sort_by=updated_at&order=desc` 的只读列表接口，由后端完成分页、排序和总数统计；不能用当前详情接口模拟全量任务列表。

## 实时性设计

“实时”在当前阶段采用分层轮询，页面同时展示 `sampled_at` 和数据来源，不把不同数据源混成一个时间点：

| 观测内容 | 当前前端策略 | 建议目标时效 | 说明 |
| --- | --- | --- | --- |
| 实例注册、模型就绪、容量、队列、存储、网关指标 | 自动刷新开启时每 10 秒 | 10 秒内 | 全局总览的轻量快照；存储和网关子请求最多等待 3 秒，失败时局部降级，不清空其他成功数据 |
| 某个实例当前执行中的任务 | 打开详情后每 5 秒请求 `active-leases` | 5 秒内 | 重点回答“现在 task_id / work_type 在哪个实例” |
| Task ID 详情 | 用户查询时请求；后续可对非终态任务每 5 秒刷新 | 查询后立即，非终态 5 秒内 | 任务事实来自 PostgreSQL，不能用心跳在途数替代任务状态 |
| 网关 P50/P95、窗口速率、错误率 | 当前解析进程 `/metrics`；后续改用 Prometheus 查询 | 10 秒采样，窗口计算由 Prometheus 完成 | `/metrics` 是累计值，不能直接代表最近 5 分钟速率或跨重启连续性 |

当前前端图表口径：

- 实例容量横向图直接使用 `/ops/operator-instances/snapshot` 当前快照，展示占用百分比，tooltip 保留实际容量、有效租约和心跳在途数。
- 队列堆叠图使用 `/ops/queues` 的 10 秒前端会话采样，最多 30 点。
- 网关趋势图使用 `/metrics` 累计值做相邻采样差分得到请求/错误速率；P95 从 `algorithm_operator_request_latency_seconds_bucket` 估算。
- 页面必须将这类前端数据标记为“本次会话”，不能标记成“最近 5 分钟”。接入 Prometheus 后，再由 BFF 返回真实窗口、采样时间和数据完整性。

## 实例与任务归属

当前页面点击实例后的数据链路如下：

```text
算子实例列表
    -> GET /ops/operator-instances/{instance_id}/active-leases
    -> leases[]
       -> work_context.task_id       = 课程任务
       -> work_context.work_type     = 当前工作类型/任务子类型
       -> work_context.node_id       = 节点
       -> work_context.item_id       = 批次或子项
       -> expires_at                 = 本次租约有效期
```

因此当前可以显示：

```text
vbas-gpu1
  course-20260831-001 / vbas_student_behavior_batch
  node=STUDENT_BEHAVIOR · item=batch-0007 · 租约至 16:08:31
```

需要注意两个事实：

- `work_type` 是工作上下文，不一定和课程枚举 `PPT`、`ASR` 完全相同。例如 `ppt_ocr_item`、`asr_transcription`、`vbas_student_behavior_batch` 都是更细粒度的执行类型，页面应同时保留原值，不能强行映射丢失信息。
- `active-leases` 只保存当前有效租约。租约释放后，实例详情不应继续声称任务仍在该实例上运行；若需要查询已完成任务“曾经在哪个实例执行”，建议在节点执行事实中持久化 `assigned_instance_id`、`lease_id`、`started_at`、`finished_at`，并增加按 `task_id + task_type` 查询的只读接口。

未绑定 `work_context` 的租约会展示为“非课程任务/上下文未绑定”，这属于真实观测事实，不应根据 `capability` 猜测 task_id。

## 建议的后端增强顺序

1. 先用现有 Control Service 接口和 gateway `/metrics` 交付只读首屏，当前 `algorithm-scheduling-ops-console` 已按此实现。
2. 增加只读聚合入口，负责并行调用 Control Service 和 gateway，并统一超时、部分失败、`sampled_at` 和 `source_status`。该入口可以是独立 BFF，也可以先放在 control-service；不建议让浏览器直接编排所有服务。
3. 在 gateway 内增加 `/ops/summary`，内部基于 Prometheus registry 或独立 Prometheus HTTP API 做窗口查询。Prometheus 只读查询层不会改变调度、租约或 A 服务接口。
4. 再增加拓扑对账接口，使“部署期望实例”和“当前注册实例”在页面中可区分；不能只用 Redis 当前注册列表推断容器一定存在。

## 网关指标注意事项

当前 `/metrics` 是进程内累计指标：请求总量和错误总量适合趋势总览，但窗口速率、P95 和跨重启连续性应交给 Prometheus 查询层。短请求量的调度证据需要结合请求计数增量、租约事件增量和 0.5 到 1 秒峰值采样，不能只看单次快照。

建议 `/ops/summary` 返回以下结构，便于前端稳定消费：

```json
{
  "window": "5m",
  "sampled_at": "2026-09-01T08:00:00Z",
  "source_status": "complete",
  "requests": { "total": 12840, "rate": 42.8, "errors": 36, "error_rate": 0.0028 },
  "capacity": { "rejected": 12 },
  "latency_ms": { "p50": 34, "p95": 96, "p99": 180 },
  "by_capability": []
}
```

## 与 A 服务的兼容性

本项目只读访问 `/ops/*` 和 `/metrics`，没有修改 `/api/course-jobs`、A 服务字段、默认端口或在线业务路由，因此不会影响 A 服务的对接。部署时只需新增前端静态资源，并确保三个观测服务允许无凭据 GET/OPTIONS CORS；若后续部署 BFF，也只改变观测入口，不改变 A 服务契约。

## 后续控制能力的技术条件

排空、恢复上线、重启实例不应由前端直接控制 Docker。正确链路是“前端 -> 带鉴权和审计的运维 API -> 受限部署控制器 -> Docker/Compose/Kubernetes”，并要求 RBAC、操作确认、幂等操作、审计事件、超时回滚和目标实例身份校验。第一阶段保持这些能力关闭，页面只显示观测边界。
