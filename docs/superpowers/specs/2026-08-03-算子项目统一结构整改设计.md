# 算子项目统一结构整改设计

## 1. 背景与目标

当前七个算法算子项目的命名、Python 包结构和启动入口不一致。其中人脸识别项目的源码目录位于项目根目录，但内部使用 `app.*` 导入，必须依赖临时软链接才能启动；实时和离线 ASR 也采用根目录下的 `api/`、`core/`、`utils/` 包；其余项目虽已有 `app/`，启动入口仍未完全统一。

本次整改的目标是：

- 统一七个项目的目录名称。
- 统一以 `app` 作为 Python 顶层包。
- 统一使用 `python -m uvicorn app.main:app` 启动。
- 同步修正 Docker、脚本、README 和其他 Markdown 文档中的路径及命令。
- 保持现有 HTTP/WebSocket 接口契约、端口和算法行为不变。
- 最终移除七个子项目各自的 `.git`，为后续将整个算法部署目录作为一个完整项目管理做准备。

## 2. 整改范围

项目目录按下表改名：

| 原目录 | 新目录 |
| --- | --- |
| `app_online` | `asr_online` |
| `asr_refine` | `asr_offline` |
| `jy-algorithm-app-facerec-service` | `facerec` |
| `jy-algorithm-app-ocr-v6-service` | `ocr` |
| `jy-algorithm-app-screen_det-server` | `screen_det` |
| `jy-algorithm-ppt-server` | `ppt_slice` |
| `jy-algorithm-tias-server` | `vbas` |

本次只调整项目名、Python 包结构、路径解析和启动方式。以下内容不在本次范围内：

- 不修改 HTTP/WebSocket 路由、请求字段和响应结构。
- 不修改算子业务逻辑、模型推理逻辑和默认端口。
- 不统一现有 `model/` 与 `models/` 目录名称。
- 不重建或重命名现有 Conda 环境。
- 不重新设计 `ai_quality`，也不将其接入新调度架构。
- 不在本次整改中初始化新的工作区根 Git 仓库。

## 3. 统一项目结构

每个正式算子使用以下基本结构：

```text
<project>/
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── api/
│   ├── core/
│   ├── services/
│   ├── schemas/
│   └── utils/
├── config.toml
├── docker/
├── scripts/
├── tests/
├── AGENTS.md
├── model/ 或 models/
└── requirements*.txt
```

项目可以根据实际功能保留 `app/entity/`、`app/engines/`、`app/models/`、`app/middleware/` 等业务目录，不为形式统一而制造空目录。

### 3.1 Python 导入规则

正式代码统一采用从 `app` 开始的绝对导入：

```python
from app.core.config import settings
from app.api.routes import router
from app.services.example import ExampleService
```

正式代码中不再使用下列旧顶层包导入：

```python
from core import ...
from api import ...
from tias import ...
```

迁移完成后不得依赖软链接、临时 `PYTHONPATH` 或必须从特定工作目录启动的隐式行为。

### 3.2 统一启动入口

所有算子必须由 `app/main.py` 暴露名为 `app` 的 FastAPI 应用对象，并统一使用：

```bash
python -m uvicorn app.main:app \
  --host 0.0.0.0 \
  --port <port> \
  --workers <workers>
```

OCR 当前的应用工厂继续保留，但 `app/main.py` 应创建并导出最终 `app` 对象；图像质量项目现有 `application.py` 中的装配逻辑应由 `app/main.py` 对外统一暴露。生命周期、模型加载顺序和接口行为必须保持不变。

### 3.3 配置和资源路径

- 支持使用 `CONFIG_PATH` 环境变量覆盖配置文件路径。
- 默认配置文件为项目根目录的 `config.toml`。
- 模型、静态资源和日志路径应基于明确的项目根目录解析，不依赖当前工作目录。
- 各项目现有 `model/` 或 `models/` 名称本轮保持不变。
- Docker 容器内路径可以按项目需要设置，但启动入口必须保持 `app.main:app`。

## 4. 各项目迁移设计

### 4.1 `asr_online`

- `svc_runtime.py` 迁移为 `app/main.py`。
- `api/`、`core/`、`utils/` 分别迁移到 `app/` 下。
- 内部导入改为 `app.*`。
- 保持实时 ASR WebSocket 路径和协议不变。

### 4.2 `asr_offline`

- 根目录 `main.py` 迁移为 `app/main.py`。
- `api/`、`core/`、`entity/`、`utils/` 分别迁移到 `app/` 下。
- 内部导入改为 `app.*`。
- 保持离线 ASR 接口、模型配置和音频处理行为不变。

### 4.3 `facerec`

- 将 `main.py`、`core/`、`router/`、`services/`、`models/`、`middleware/`、`utils/`、`static/` 迁移至 `app/`。
- `ai_models/`、`media/` 和 `config.toml` 保留在项目根目录。
- 修正项目根路径计算，确保模型路径不因源码多一层 `app/` 而失效。
- 删除对临时 `app` 软链接的依赖。

### 4.4 `ocr`

- 保留现有 `app/` 结构。
- 将应用工厂结果统一暴露为 `app.main:app`。
- 同步修改 Docker 和本地启动命令。

### 4.5 `screen_det`

- 保留现有 `app/` 结构。
- 由 `app/main.py` 统一暴露应用对象。
- 将现有 `app.application:app` 启动命令改为 `app.main:app`。

### 4.6 `ppt_slice`

- 保留现有 `app/` 结构。
- 修正项目目录名、Docker、启动脚本和文档路径。
- 保持视频切片任务接口和回调格式不变。

### 4.7 `vbas`

- 原 `tias/` 正式算子源码迁移至 `app/`。
- 正式代码导入由 `tias.*` 迁移为 `app.*`。
- 删除原 `ai_quality/`，不在 `vbas` 中保留副本。
- 正式 `vbas/app` 不允许依赖已抽离的视觉调度器。
- 在工作区根 `AGENTS.md`、`vbas/AGENTS.md` 和相关 README 中记录视觉调度器已迁往独立项目。

`ai_quality` 是旧版 VBas 内部用于调度 TIAS、聚合检测结果及写库的实现。该能力已经抽离到 `/Users/zhangshen/Documents/workspace/jy-vision-orchestrator-server`，其 Git 仓库地址为 `git@github.com:ZhangShen55/jy-vision-orchestrator-server.git`。新的算法调度架构通过独立项目承接相关职责，`vbas` 只保留视觉算法推理能力。

## 5. 文档和部署文件同步

目录迁移必须同时检查并更新：

- 每个项目的 `README.md`。
- `docs/` 下所有包含旧项目名、旧路径或旧启动入口的 Markdown 文件。
- Dockerfile、Compose、Nginx 配置和容器启动脚本。
- 构建、模型校验、加密、测试和部署脚本。
- 示例命令、绝对路径、挂载路径、`COPY`、`WORKDIR`、`CMD` 和 `ENTRYPOINT`。
- 测试代码、回调脚本和本地快速启动脚本。

迁移后使用全文搜索确认正式范围内不存在旧目录名、旧模块入口和过期命令。历史说明中确需保留旧名称时，应明确标注为历史名称。

### 5.1 `AGENTS.md` 分层约定

统一使用标准文件名 `AGENTS.md`（复数），不使用 `AGENT.md`。工作区设置两级说明：

- 根目录 `AGENTS.md`：记录七个算子的项目地图、统一目录规范、统一启动方式、公共兼容约束、文档同步规则和跨项目边界。
- 每个项目的 `AGENTS.md`：记录该算子的职责、入口、默认端口、Conda 环境、配置与模型位置、主要接口、测试及真实推理命令、禁止事项和外部依赖。

`AGENTS.md` 是提供给开发代理和自动化 Harness 的长期操作说明，不作为逐次改动日志。只有下列长期规则发生变化时才更新相应 `AGENTS.md`：

- 项目职责或边界变化。
- 目录、入口、启动或部署方式变化。
- 配置、模型或关键外部依赖位置变化。
- 必须执行的测试、验证命令或安全约束变化。
- HTTP/WebSocket 契约兼容要求变化。

普通代码修改不写入 `AGENTS.md`。普通改动由 Git 提交记录；对外行为或发布版本变化写入 `CHANGELOG.md` 或对应设计文档；安装、部署和使用方式变化同步更新 `README.md`。

## 6. Git 元数据处理

当前七个算子目录各自包含 `.git`，工作区根目录不是 Git 仓库。为保留迁移期间识别已有修改和回退的能力，处理顺序为：

1. 迁移前记录每个子项目的 `git status`。
2. 使用各子项目现有 Git 元数据检查目录移动及代码差异。
3. 完成七个项目的迁移、测试和真实推理。
4. 再次确认每个项目的文件完整性和测试结果。
5. 最后删除七个子项目各自的 `.git` 目录。
6. 本次不自动执行 `git init`，后续建立完整项目仓库时另行设计根 `.gitignore`，避免模型、媒体、日志和结果文件被错误纳入版本控制。

删除 `.git` 后，子项目原有本地提交历史和 Git 回退能力不再保留，因此该操作必须位于全部验证之后。

## 7. 迁移顺序

按风险从低到高逐个迁移：

1. `ocr`
2. `screen_det`
3. `ppt_slice`
4. `facerec`
5. `asr_online`
6. `asr_offline`
7. `vbas`

每次只迁移一个项目。当前项目完成静态检查、自动测试、启动和真实推理后，才能进入下一个项目。

## 8. 验收标准

每个项目必须通过以下检查：

1. `python -m compileall app` 成功。
2. `from app.main import app` 成功。
3. 项目现有自动测试通过。
4. 新增的统一入口、配置路径和导入测试通过。
5. 迁移前后 HTTP/WebSocket 路由、方法和协议保持一致。
6. 使用 `python -m uvicorn app.main:app` 在原端口启动成功。
7. 健康检查成功。
8. 使用真实测试数据完成一次推理：
   - `asr_online`：WAV 分块 WebSocket 转写。
   - `asr_offline`：WAV 离线转写。
   - `facerec`：使用已有人员图片完成识别。
   - `ocr`：使用测试图片完成 OCR。
   - `screen_det`：通过 `detect_all` 完成单图检测。
   - `ppt_slice`：完成视频切片并验证图片输出。
   - `vbas`：不经过外部视觉调度器，直接完成学生和教师检测。
9. 正式启动不依赖软链接或临时包别名。
10. README、Docker 和路径相关 Markdown 文档已同步。
11. 根目录和七个项目均具有内容准确、作用域明确的 `AGENTS.md`。
12. `vbas` 中不存在 `ai_quality`，且文档已指向独立视觉调度器项目及其 Git 地址。

## 9. 失败处理

- 某个项目验收失败时停止迁移后续项目。
- 只处理当前项目本轮引入的目录、导入、路径和启动问题，不修改算法行为来规避测试。
- 必要时依据迁移前状态反向恢复当前项目的目录移动和本轮修改。
- 不回退或覆盖用户迁移前已有的修改。
- 只有七个项目全部验收完成后，才允许删除子项目 `.git`。
