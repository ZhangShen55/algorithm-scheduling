# 里程碑 2B 三卡部署验证设计

## 1. 文档目的

本文定义算法功能调度平台里程碑 2B 的部署验证方案。当前里程碑先补齐可复现的服务器部署层，
在一台具备三张 NVIDIA GPU 的 x86_64 服务器上构建并运行四个平台服务、基础设施和 24 个真实
算子实例，并形成可审计的 GPU、注册、容量、推理和业务抽样证据。

里程碑 2A 已经使用真实 PostgreSQL、Redis、Kafka 和 HTTP 契约 Stub 贯通：

```text
POST /api/course-jobs
-> PostgreSQL + Outbox
-> Kafka
-> DAG
-> control-service 容量租约
-> HTTP Stub
-> Worker 持久化节点状态
-> GET 查询结果
```

里程碑 2B 不重做 2A。本阶段先验证真实算子的部署和实例调度基础，再逐条接入 PPT、ASR、视觉
和在线业务泳道。PPT 算子自身已经完成优化不等于 `PPT -> OCR -> 关键词` 泳道已经接入
orchestrator 运行时；任何完整泳道结论仍必须由真实端到端证据支持。

### 2.2 基础设施与平台服务

同机部署以下基础设施：

- PostgreSQL：课程任务、节点、结果、Outbox 和审计事实。

- `control-service`

- `vision-orchestrator-service`
- `online-gateway-service`

四个服务仍是独立进程和容器。离线通用调度依赖 control 与 orchestrator；视觉离线泳道依赖

## 3. 非目标与兼容边界

本部署里程碑不执行以下工作：

- 不引入 Kubernetes、Service Mesh 或多机高可用。
- 不修改 A 服务稳定字段、任务类型、HTTP 路径或 WebSocket 路径。
- 不让 ScreenDet 进入离线课程 DAG；它仍属于在线网关图片链路。
- 不给在线图片接口增加 RTSP 接入或平台抽帧。
- 不把 VBas 重新改回课程级聚合服务；VBas 仍只负责帧级推理。
- 不把模型文件提交到 Git。
- 不把测试环境的成功扩大解释为生产高可用验收。

## 8. GPU 绑定与真实性门槛

预检确认服务器安装了 NVIDIA Container Runtime，但 Docker `Runtimes` 输出未显式列出
`nvidia`。正式构建前必须先用 CUDA 容器执行 `nvidia-smi`，确认 Compose device reservation
可以让容器看到目标卡。

每个 GPU 实例必须同时满足：

1. 容器只看到指定的一张物理卡。
2. 容器框架报告 CUDA 可用且设备数为 1。
3. 算子配置和运行日志显示模型加载到容器内 `cuda:0`。
4. 调用真实推理时，宿主机 `nvidia-smi` 能观察到该容器对应进程和显存变化。
5. control-service 注册记录的 `PLATFORM_GPU_ID` 与物理卡编号一致。

### 8.1 `nvidia-smi` 进程名称

Docker `container_name`、平台 `instance_id` 和 `nvidia-smi` 的 `Process name` 是三个不同概念。
`nvidia-smi` 展示创建 CUDA Context 的宿主机进程名称；普通 Uvicorn 启动通常只显示 `python`，
仅修改容器名不会改变该列。

本服务器已完成最小实测：容器使用以下形式启动 Python 并创建 CUDA Context：

```bash
exec -a asr_offline python -c 'import torch,time; torch.zeros(1,device="cuda"); time.sleep(30)'
```

宿主机查询实际返回：

```text
2502146, asr_offline, 404 MiB
```

因此 GPU 算子的最终启动脚本统一使用 `exec -a <operator_name> python -m uvicorn ...`。稳定名称为：

```text
asr_offline
asr_online
ocr
vbas
facerec
screen_det
```

`ppt_slice` 和 `text_analysis` 使用 CPU，不会出现在 `nvidia-smi` 的 Compute Processes 中；它们
仍可使用相同的命名启动方式改善宿主机进程排查，但不作为 GPU 验收证据。

进程名不得包含 GPU 编号。物理 GPU 和具体实例通过以下信息联合确定：

- `nvidia-smi` 的 GPU index、PID、Process name 和显存。
- `docker top`、容器 PID 与宿主机 PID 映射。
- 容器名和 `PLATFORM_INSTANCE_ID`，例如 `asr-offline-gpu1`。
- control-service 注册记录中的 `PLATFORM_GPU_ID=1`。

每个容器保持一个 Uvicorn worker。若以后增加 worker，必须重新验证 CUDA Context 实际由哪个子进程
创建，以及 `exec -a` 名称是否继续出现在每个 GPU 子进程上，不能沿用本阶段结论。

ASR 和 VBas 当前存在 CUDA 不可用时回退 CPU 的实现。部署模式必须增加 GPU fail-fast：配置要求
GPU 时，CUDA 不可见或模型没有进入 GPU 必须导致启动/readiness 失败，不能静默使用 CPU。
OCR、FaceRec 和 ScreenDet 同样执行明确设备验证。

每张卡按以下顺序渐进启动：

```text
CUDA 容器预检
-> 单个算子启动、真实推理、显存记录
-> 逐个增加剩余算子
-> 六个算子全部常驻
-> 六个算子并发真实推理
```

若单卡无法同时容纳六个模型，不回退 CPU，也不擅自降低模型规格。先记录每个算子的常驻和推理
峰值显存，再提出卡间布局或互斥部署调整，由用户确认后变更目标拓扑。

## 9. 构建和磁盘保护

- 镜像逐个构建，每个镜像通过单实例真实推理后再构建下一个。
- 每次构建前后记录镜像大小、Build Cache 和剩余空间。
- 根分区可用空间低于 100 GiB 时暂停构建、模型传输和课程视频下载。
- 不执行全局 `docker system prune`。
- 不删除服务器既有业务镜像、容器、网络和卷。
- 课程视频按代表样本和批次获取，不预先下载整个课程站点。
- `/data/course` 只清理由本次 Harness 创建且已到终态的任务目录。
- `/data/result` 作为长期结果目录保留。

## 10. 业务泳道和 2B 分段

完整泳道如下：

| 类别 | 泳道 |
| --- | --- |
| PPT 离线 | 下载 P -> PPT Slice -> 共享切片/manifest -> OCR -> `/v1/extract_keywords` -> PostgreSQL |
| ASR 离线 | 下载 T -> FFmpeg WAV -> ASR v1.1.8 -> `/v1/course_overviews` -> PostgreSQL |
| 教师行为离线 | 下载 T -> 视觉命令 -> 自适应抽帧 -> VBas -> 区间聚合 -> 证据/结构化结果 |
| 学生行为离线 | 下载 S -> 自适应抽帧 -> VBas -> 人数/到课率/区域聚合 -> 证据/结构化结果 |
| VBas 在线图片 | A Base64 图片 -> online gateway -> 容量租约 -> VBas 教师/学生推理 |
| 图像质量在线 | A Base64 单图 -> online gateway -> ScreenDet `/detect_all` |
| 人脸 | A 管理 `/persons` 或提交识别图片 -> online gateway -> FaceRec + MongoDB |
| 实时 ASR | A WebSocket -> online gateway 长租约和会话粘性 -> ASR Online |

2B 按以下顺序推进：

1. **2B-Deploy**：本文定义的基础设施、平台、镜像、24 实例、注册、GPU 和单算子验证。
2. **2B-PPT**：真实 `PPT -> OCR -> 关键词` 离线泳道。
3. **2B-ASR**：真实 `T -> WAV -> ASR -> 课程脑图` 离线泳道。
4. **2B-Vision**：教师和学生自适应视觉泳道。
5. **2B-Online**：在线 VBas、ScreenDet、FaceRec、人脸库管理和实时 ASR。
6. **2B-Full**：组合任务、实例下线恢复、优先级、容量和压力测试。

2B-Deploy 通过并不表示后五项已经通过。OpenSpec 中真实算子接入、视觉运行时、在线资源和完整产品
验收任务应按证据分别更新，不可一次性勾选。

## 12. B 级验收标准

用户确认采用 B 级验收：除了接口和调度正确，还对多节真实课程结果进行人工抽样复核。

### 12.1 部署证据

- 基础设施与四服务健康/readiness。
- 24 个算子实例注册、首次心跳、容量和 GPU/CPU 标签。
- 每个 GPU 实例的 CUDA、真实推理和宿主机显存证据。
- 镜像标签、commit label、模型清单和端口映射。

### 12.2 功能证据

- 八种算子均完成至少一次真实业务调用。
- 所有离线与在线泳道分别产生真实结果。
- 文件结果只在预期目录出现，结构化结果存入 PostgreSQL。
- PPT Slice 输出原子 manifest、动态区间和长期切片。
- FaceRec 不保存人物原图但 embedding 和识别有效。

### 12.3 调度证据

- 三个同能力实例均实际收到过请求，不只验证注册列表。
- 容量用尽时请求等待或返回已定义错误，不绕过租约。
- `URGENT` 优先于尚未执行的 `NORMAL`，不抢占运行节点。
- 实例排空、停止、TTL 离线和恢复后路由正确。
- 实时 ASR 一条 WebSocket 会话粘在同一实例。
- 在线请求不进入 Kafka，单个请求不拆给多个实例。

### 12.4 人工业务抽样

对多节课程至少抽样检查：

- PPT：切片覆盖、重复页、黑屏、疑似视频/滚动排除及漏页。
- OCR：每张切片的文本可读性、明显错字和公式结果。
- 关键词：与当前 PPT 页内容的相关性。
- ASR：文本可读性、明显漏字/错字、说话人和情绪字段。
- 课程脑图：主题、知识点和层级与 ASR 内容的一致性。
- 教师行为：站、坐、板书、讲授区间和间断容忍。
- 学生行为：人数稳定性、到课率、区域数据及兜底标识。
- 视觉证据：高光和消极时刻图片与结构化区间一致。

报告记录 `通过`、`明显误检`、`明显漏检` 和 `不可判定`，并保留允许留存的证据路径。不计算准确率、
召回率等量化指标；若未来要求 C 级验收，必须另行制作标注真值。

## 13. 压力测试

压力逐级增加：

```text
单请求 -> 3 并发 -> 10 并发 -> 30 并发 -> 目标上限 100 并发
```

离线课程并发和在线请求并发分别统计，不能把长视频任务数与单图 QPS 混成一个指标。每一级记录：

- 吞吐量
- P50/P95/P99
- 业务错误率与 HTTP/WebSocket 错误率
- GPU 显存、利用率和进程归属
- CPU、内存、磁盘和网络
- Kafka Lag、Outbox 积压和节点等待数量
- 各实例 inflight 与容量租约

出现以下任一条件立即停止升压：

- GPU OOM 或模型进程退出。
- 持续性业务错误或错误率明显上升。
- 根分区可用空间接近 100 GiB 门槛。
- Kafka Lag 或任务积压持续增长且无法回落。
- 现有基础设施或平台 readiness 失败。

压力测试的目标是找出稳定容量，不是必须达到 100 并发。未达到的最高并发和瓶颈必须如实记录。

## 15. 实施顺序

1. 完成部署 Compose、共享配置、GPU fail-fast、VBas 端口和自动化验证脚本。
2. 运行本机静态测试、Compose 解析、单元测试和 OpenSpec 严格校验。
3. 提交并推送 2B 分支。
4. 在服务器记录现有容器快照并暂停已授权容器。
5. 验证 CUDA 容器 GPU 可见性，创建 `/data/course` 和 `/data/result`。
6. 使用 Deploy Key 克隆并固定提交。
7. 通过 `scp` 传输模型和所需服务器配置，核对清单。
8. 逐个构建 8 个版本化镜像。
9. 逐卡验证 18 个 GPU 实例，再验证 6 个 CPU 实例。
10. 启动基础设施、四个平台服务和 24 个算子实例，检查注册/容量。
11. 按 2B-PPT、2B-ASR、2B-Vision、2B-Online、2B-Full 依次接线和验收。
12. 形成 B 级人工抽样报告和压力报告，复审剩余风险。
13. 停止本项目测试容器并按快照恢复原先运行的业务容器。

## 16. 完成定义

2B-Deploy 只有同时满足以下条件才算完成：

- 部署文件可以从干净克隆重复解析和执行。
- 8 个镜像按规定标签完成构建，并记录 commit label。
- 24 个实例均能启动、注册和心跳。
- 18 个 GPU 实例全部通过 GPU 真实性验证，未静默回退 CPU。
- 8 种算子分别完成真实推理。
- 单卡六算子并存和并发测试有显存证据；若不能并存，已明确记录并经用户批准调整。
- 磁盘保护、既有容器快照和恢复流程均有证据。
- Harness、OpenSpec 和设计文档只勾选实际验证完成的任务。

后续完整里程碑 2B 还需逐条完成所有业务泳道、B 级人工抽样和分阶段压力测试。
