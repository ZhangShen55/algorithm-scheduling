# 里程碑 2B 真实业务泳道与完整验收设计

> 日期：2026-08-18
> 状态：已确认，待实施计划
> OpenSpec：`close-platform-runtime-and-harness-gaps`

## 1. 背景与基线

里程碑 2B 已在 `192.168.29.11` 完成一次真实三卡部署。权威报告固定在 release
`v1.0_260812/7efac20cf980ee64ea78fe297af6dfdfb2df5b28`，结果为 332 条用例中
83 条通过、6 条失败、243 条“未执行及原因”。243 条由 217 条反例和 26 条压力用例组成。

24 个算子实例均完成注册、首次心跳、`ONLINE` 和 `model_ready=true`；18 个 GPU 实例中
15 个通过逐实例证据。FaceRec 三实例失败的直接原因是 Harness 在只提供 `python3` 的镜像内
调用了 `python`。同一镜像使用 `python3` 的直接 FastDeploy 探针已返回
`framework_gpu_available=true`。因此下一阶段需要修复证据执行合同并重新验收，不能修改旧报告。

当前通用基础闭环已经使用真实 PostgreSQL、Redis、Kafka、`control-service`、
`orchestrator-service` 和 HTTP 契约 Stub 验证，但真实 PPT、ASR、视觉和在线业务泳道尚未
贯通。现有 OpenSpec 变更为 `35/62`，未完成任务已经覆盖这些真实泳道。

## 2. 目标

本阶段完成以下可验证结果：

1. 在新 Git SHA 和新 release 目录下关闭 FaceRec 三卡 GPU 证据缺口。
2. 实现 PPT、ASR、视觉和在线四类真实业务泳道，不以直接调用算子 Smoke 冒充平台泳道。
3. 建立 217 条反例和 26 条压力用例的机器可执行目录、前置条件和证据合同。
4. 最终实际执行全部 243 条用例；最终验收不允许保留“未执行及原因”。
5. 失败必须如实写入 Harness。独立工作可继续，但失败阶段不得标记完成。
6. 每个阶段形成中文 Conventional Commit 并推送；报告按 Git SHA 不可变归档。

## 3. 非目标

- 不改变 A 服务已经确认的字段、任务类型、整数状态和 HTTP 200/业务码边界。
- 不改变现有算子 HTTP/WebSocket 业务路径，PPT 已批准的内部共享路径合同除外。
- 不引入 Kubernetes、多机高可用、Service Mesh 或通用工作流产品。
- 不把在线图片或实时 ASR 放入 Kafka，也不为在线图片增加 RTSP/抽帧。
- 不宣称模型准确率、召回率或业务效果达到未提供真值的数据指标。
- 不覆盖旧 release 报告，不删除 `/data/result`、模型、人脸库或既有业务数据。

## 4. 方案选择

### 4.1 采用方案：一个 OpenSpec、五个连续验收阶段

继续使用现有 `close-platform-runtime-and-harness-gaps`，在其中补充分期、依赖和完成门槛。
每个阶段拥有独立 Harness 场景或执行批次，但共同收敛到一个完整产品验收。

该方案避免复制已经存在的规格，同时允许每条泳道独立定位、修复和重跑。

### 4.2 未采用：一次实现、一次总验收

一次性修改四个服务和八个算子后再运行 243 条用例，会把部署、数据、契约、并发和模型问题
混在同一故障面中，无法可靠判断失败归属。

### 4.3 未采用：拆成四个平行 OpenSpec

四个独立变更会重复服务边界、状态机、Harness 和最终验收规格，并增加跨变更状态不一致风险。
如后续某条泳道需要改变已经确认的业务契约，再为该契约单独提出变更。

## 5. 实施阶段和依赖

### 阶段 1：2B FaceRec 证据关闭

- GPU 探针不得假定容器存在 `python`；使用明确配置或经过验证的 `python3`。
- 基于修复后的新 Git SHA 构建和校验相关镜像，不复用旧 SHA 的通过结论。
- 在 GPU 0、1、2 分别验证 FaceRec 框架 GPU 可用性、真实请求期间宿主 CUDA PID、容器
  cgroup、GPU UUID、注册实例和容量恢复。
- 复核 24 个实例注册及 18 个 GPU 实例证据，旧 release 的 6 条失败保持不变。
- 执行不依赖业务泳道的部署、注册、GPU、文件安全、容量和恢复类反例/压力用例。

阶段门槛：FaceRec 三实例产生完整新证据；部署层用例没有“未执行及原因”。

### 阶段 2：PPT 与 ASR 离线泳道

PPT 数据流：

```text
A 提交 PPT -> control 写任务与 Outbox -> Kafka -> orchestrator 初始化 DAG
-> 下载 P 到 /data/course/{task_id} -> 申请 ppt_slice 租约
-> ppt_slice 写 /data/result/{task_id}/ppt + 原子 manifest + 一次终态通知
-> manifest 对账 -> 按 ppt_image_id 调 OCR -> 按 ppt_image_id 调关键词
-> PostgreSQL 保存结构化结果 -> A 查询任务和节点结果
```

ASR 数据流：

```text
A 提交 ASR -> control 写任务与 Outbox -> Kafka -> orchestrator 初始化 DAG
-> 下载 T 到 /data/course/{task_id} -> 提取 WAV -> 申请 asr_offline 租约
-> 调用 /v1.1.8/seacraft_asr -> 保存完整业务响应和 effective_params
-> 使用已保存 segments 调课程脑图 -> 保存完整嵌套响应 -> A 查询结果
```

同一次 `submission_id` 中 ASR 与教师行为可以共享一次 T 下载；后续独立提交必须重新下载，
不得为了未来请求长期保留 T 或 WAV。PPT/ASR 完成后只清理 `/data/course/{task_id}` 的临时所有物，
保留 `/data/result/{task_id}` 和数据库结果。

阶段门槛：PPT-only、ASR-only 和 PPT+ASR 均通过真实 A API、Kafka、DAG、租约、真实算子和
查询接口完成；相关反例和压力用例全部执行。

### 阶段 3：离线视觉泳道

`orchestrator-service` 只发布课程级视觉命令；`vision-orchestrator-service` 负责 T/S 本地抽帧、
自适应检测、结果聚合和证据图片。单帧循环不得拆成 Kafka 消息。

教师行为采用可配置粗扫间隔，并按 10/5/2/1 秒逐步细化候选边界；板书和坐姿使用已确认的
短中断合并规则。学生行为聚合人数、到课率和前后排结果。提供区域时使用
`front_points`/`back_point`；未提供时生成一次配置范围内的稳定兜底值，并返回
`front_region_provided`/`back_region_provided`。

精选高光或消极时刻证据图片保存到 `/data/result/{task_id}/vision`，普通抽帧留在临时目录。
没有某类行为时返回成功终态和空区间，不将“没有检测到该行为”当作系统失败。

阶段门槛：teacher-only、student-only 和组合视觉任务经真实 Kafka visual command/event、VBas
租约、细化轮次、聚合、结果查询和证据留存完成；相关反例和压力用例全部执行。

### 阶段 4：在线业务泳道

- `/api/online/vbas/analyze`、`/api/online/face/recognize`、`/api/online/image-quality/detect` 按整个请求选择
  一个实例，不拆分多图；上游按约定尽量一图一请求。
- 请求携带 Base64 图片，网关不接入视频流、不抽帧、不写 Kafka、不创建离线课程任务。
- 实时 ASR WebSocket 在会话建立时取得 `asr_online` 实例和粘性租约，整个会话保持实例一致，
  断开后释放。
- A 通过在线网关管理 FaceRec 人脸库；FaceRec/MongoDB 继续拥有人脸 embedding。默认
  `save_person_photo=false`，不影响 embedding 入库和识别。

阶段门槛：三个在线图片入口、实时 ASR 和人脸管理代理均通过真实租约与算子完成；验证容量
耗尽、并发路由、断连、实例摘除和恢复；相关反例和压力用例全部执行。

### 阶段 5：243 条完整验收

- 重新执行全部 217 条反例和 26 条压力用例，而不是只聚合前几阶段的历史状态。
- 运行 PPT-only、ASR-only、teacher-only、student-only、四类组合任务和全部在线场景。
- 验证相同任务结果复用、后续 task type 追加、优先级、重复消息、重启、容量不足、清理和审计。
- 最终 cases 清单中不得存在“未执行及原因”。任何失败都使总报告保持失败。

阶段门槛：新 release 的报告、原始证据和汇总一致；报告结论完全由用例事实生成。

## 6. 反例与压力用例执行模型

每条用例必须具有稳定 `case_id`，并声明：类别、所属阶段、前置条件、执行动作、预期结果、
超时、清理动作和证据文件。用例分为以下归属：

| 归属 | 主要内容 |
| --- | --- |
| 部署与 GPU | 镜像身份、GPU UUID/PID/cgroup、注册、恢复、磁盘和文件边界 |
| PPT/ASR | 下载、共享、manifest、回调、租约、子项进度、ASR 参数与结果 |
| 视觉 | 抽帧、细化、矛盾帧、空行为、区域兜底、证据和视觉事件 |
| 在线与人脸 | Base64、请求级路由、WebSocket 粘性、人脸库代理和断连恢复 |
| 组合与容量 | URGENT/NORMAL、重复提交、实例耗尽、并发上限和服务重启 |

压力用例采用逐级加压和有界超时。它们必须记录请求量、并发、成功/失败分布、业务码、延迟、
实例选择、GPU/CPU/内存和恢复结果。没有已确认吞吐 SLO 的场景只评价正确性、容量合同和资源
稳定性，不把临时测得的吞吐量升级为产品承诺。

## 7. 失败处理与继续规则

1. 用例失败立即保存命令、请求、响应、日志摘要、实例和资源证据，状态写为“失败”。
2. 失败不得被后续聚合覆盖，也不得改写同 SHA 报告；修复后使用新 SHA 和新目录重跑。
3. 与失败无依赖的开发和测试可以继续；依赖该能力的阶段不得标记完成。
4. 涉及数据删除、错误 GPU 设备、磁盘耗尽或既有业务容器安全的失败必须停止相关部署动作。
5. 代码缺陷修复进入中文规范提交；环境限制仍记录 Harness，不伪造代码通过。

## 8. Harness 与 OpenSpec 记录

Harness 使用以下证据层级：静态/单元、真实数据库与 Redis、真实 Kafka、服务运行、真实算子、
三卡部署、完整业务泳道、压力与恢复。每项结论只提升到实际取得的层级。

每个 release 以 `release tag + 40 位 Git SHA` 建立不可变证据根，至少保存：

- 环境、镜像 revision、容器和 GPU 身份；
- API/WebSocket 请求摘要和响应；
- PostgreSQL/Outbox/节点状态与 Kafka offset；
- Redis 租约选择和释放；
- `/data/course` 清理与 `/data/result` 留存；
- 反例/压力原始结果、聚合报告和失败原因。

OpenSpec 不另建重复变更。实施计划将现有 4.7-4.12、5.1-5.7、6.1-6.5、9.1-9.6 和
10.1/10.3/10.4 映射到上述五个阶段。任务只有在对应运行证据产生后才能勾选。

- 217 条反例和 26 条压力用例全部实际执行；
- 最终报告没有“未执行及原因”，失败数为零；
- OpenSpec 严格校验、完整测试、Compose、镜像身份和 Harness 一致性检查通过；
- 所有提交已使用中文 Conventional Commit 推送，旧 release 证据保持不可变。
