## Context

v1.0.1 每收到一个约 0.48 秒 PCM 块便同步调用在线 Paraformer，并以连续两个空识别结果作为字幕段结束条件；文本超过三个字后还会对不断增长的全文重复执行标点模型。它没有整句声学纠正能力，而且同步模型调用会阻塞 WebSocket 事件循环。server12 的 50 路、每路 30.24 秒快速测试中，v1.0.1 partial p95 为 13.06 秒并出现持续 15 秒无响应，说明 v1.0.1 也必须先测定实际容量，不能直接认定支持 50 路。

v1.0.2 增加 FSMN-VAD 和 SeACo 句末二次识别，v1.0.3 又增加渐进 SenseVoice 纠正。它们的试验结论不能通过改变既有接口继续迭代，因此本 change 新增 v1.0.4，并把 v1.0.1、v1.0.2、v1.0.3 作为不可修改的回归基线。server12 可通过 `192.168.29.12` 访问，具备三张 RTX 4090；Mac 使用 `asr` Conda 环境，server12 使用 `/root/workspace/asr_online` 和同名环境。

## Goals / Non-Goals

**Goals:**

- 新增与既有请求和响应字段兼容的 `/v1.0.4/seacraft_asr_online`。
- 复用 v1.0.1 的低开销断句方式，每个自然字幕段最多提交一次 SenseVoice 句末纠正。
- 纠正排队、超时或失败不得阻塞音频接收；过载时牺牲纠正覆盖率而不是实时 partial。
- 避免每个 0.48 秒块对增长中全文重复执行标点，并量化优化前后的延迟和容量。
- 在 server12 上完成可复现的单路全量、并发容量、纠正覆盖率、协议时间轴和资源稳定性验证。

**Non-Goals:**

- 不修改 v1.0.1、v1.0.2、v1.0.3 的实现、配置语义和接口行为。
- 不给 v1.0.4 增加 FSMN-VAD、VAD pending/merge、每八字纠正或周期性渐进纠正。
- 不修改 `online_gateway_service`，不在本 change 宣布生产切流。
- 不承诺单实例 50 路；容量数字只接受 server12 实测结果。
- 没有人工标注参考文本时，不使用主观样例宣称 CER/WER 提升。

## Decisions

### 1. 新路由隔离既有接口

v1.0.4 使用独立会话函数和独立配置前缀，复用经过测试的文本合并、纠正调度等通用工具，但不让既有三个路由进入新分支。这样可以对照、回滚并避免修正实验改变现网语义。

每个 v1.0.4 字幕段在创建时生成一个稳定 `key`；同段 partial 与最终结果复用该 `key`。字段集合仍严格为 `key/text/finished/bg/ed`，`finished=true` 仍只表示字幕段结束。

### 2. 不增加 VAD，以两次空结果建立候选结束窗口

在线结果从非空变为空的第一次事件建立候选结束：冻结当前段 PCM 快照并非阻塞地提交一次 SenseVoice。连续第二次空结果确认段结束，两次事件按正常 0.48 秒输入节奏提供约 0.48 秒纠正抢跑时间。

若第二次空结果前恢复非空语音，则取消候选；已经执行的结果通过 `connection_id`、`key`、revision 和 PCM 结束样本位置校验后作为 stale 丢弃。每段设置有界 PCM 和最大时长；保护性切段可以提交一次纠正，但只在既定极短预算内采用结果，不能为了纠正无限等待。

替代方案是引入 FSMN-VAD，但这会重复 v1.0.2/v1.0.3 的每块额外推理和缓存复杂度，与本 change 的低开销目标冲突。

### 3. 在线完成优先于纠正覆盖率

第二次空结果到达时按以下顺序决定最终文本：

1. 同一段、同一边界的 SenseVoice 结果已经就绪时直接采用；SenseVoice 自带标点，不再调用独立标点模型。
2. 结果正在运行且在线推理没有积压时，最多等待可配置的极短 final budget，初始值为 100 ms。
3. 结果未就绪、队列满、超时或失败时，立即使用在线文本加最终标点发送 `finished=true`；晚到结果不得再次改写已完成段。

提交操作必须非阻塞。每会话最多一个任务在途和一个 latest-only pending；队列有界，候选任务可丢弃，并记录 submitted/applied/stale/skipped/failed/fallback。该模式提供 best-effort 纠正，无法在单卡满载时同时保证每段纠正和最高并发。

### 4. 在线推理不阻塞事件循环，但不虚构吞吐提升

v1.0.4 将同步在线模型调用交给受控的模型执行入口，WebSocket 事件循环继续收发和执行超时检测。单个 FunASR 模型实例只由一个受控执行通道访问，避免对非线程安全 cache 或模型对象并发调用。

受控执行入口改善事件循环响应和会话公平性，但不会凭空增加 GPU 吞吐；若到达率超过模型处理能力仍会积压。因此必须先测 v1.0.1 基线，再按相同音频、节奏和判定口径测试 v1.0.4。跨会话 micro-batch 只有在独立原型证明 FunASR 在线 cache 能正确分离后才能启用，不作为本 change 的默认实现。

### 5. 降低 partial 标点频率

v1.0.4 仅在稳定文本新增达到配置阈值或距离上次标点达到配置时间时更新 partial 标点，其他块复用已知标点前缀并追加原始增量。默认阈值为新增八个中英文单位或两秒；最终在线降级文本仍执行一次完整标点。这样减少对增长全文的重复计算，不改变 v1.0.1 的既有行为。

### 6. 纠正设备可隔离，远端验收优先使用独立 GPU

新增可选的纠正设备配置；未设置时使用主 `device`，Mac 可继续使用 CPU。server12 验收配置把在线 ASR 放在一张 RTX 4090、SenseVoice 放在另一张 RTX 4090，避免长句纠正 kernel 与每 0.48 秒在线推理争用同一设备。独立进程但共用同一 GPU 不能视为资源隔离。

设备配置不得改变 v1.0.1、v1.0.2、v1.0.3 的路由逻辑；若复用现有 SenseVoice 调度器，必须用回归测试证明 v1.0.3 协议和结果语义不变。模型加载失败必须使服务启动失败，禁止静默切回 CPU。

### 7. 分层验证并保留可审计报告

本地先运行编译、应用导入、单元和协议测试。同步到 server12 后校验关键文件哈希，后台启动 8084 并允许最多五分钟加载模型，健康检查连续两次成功后才开始测试。客户端在 server12 本机连接 `127.0.0.1:8084`，消除 Mac 到服务器网络波动。

远端依次执行：四个接口短音频回归；v1.0.1/v1.0.4 同条件 30 秒容量探测；边界通过点和首个失败点十分钟复验；v1.0.4 单路完整 47 分钟正确性与稳定性测试。实时通过要求所有客户端完整发送、无 stalled/OOM/协议或时间轴错误、partial p95 不超过 1 秒、finished p95 不超过 1.5 秒且无持续缓存增长。v1.0.4 最大稳定并发不得低于同轮 v1.0.1 基线，否则该实现不满足实时优先目标。

报告列出所有纠正位置及 submitted/applied/fallback/skipped/stale/failed 数量和覆盖率。无人工标注时只描述文本差异，不断言准确率提升。原始输出保存在忽略目录，汇总报告纳入 change。

## Risks / Trade-offs

- [候选结束是假阳性，提前消耗纠正资源] → 只允许每会话单在途和 latest-only，恢复语音后使旧 revision 失效，队列拥堵时跳过。
- [SenseVoice 在第二次空结果前未完成] → 最多等待 100 ms 且仅在在线无积压时等待，否则立即 fallback；报告实际覆盖率。
- [同卡 SenseVoice 抢占在线 GPU] → server12 首选独立 GPU；同卡模式通过队列准入降级，但不宣称强隔离。
- [受控串行入口仍无法达到高并发] → 报告真实容量；后续若需 50 路，通过多实例会话粘性或验证后的 micro-batch 另立 change。
- [稳定 `key` 与现有消费者假设不一致] → v1.0.4 是新路径，增加同段 key、唯一 finished 和替换语义测试，暂不接入网关。
- [长段 PCM 导致内存增长] → 采用样本数硬上限，结束、取消和断连时释放，并进行 47 分钟 RSS/GPU 稳定性检查。
- [远端遗留服务占用 GPU] → 启动前验证 8084 所有权，测试使用独立进程组，finally 阶段终止进程组并核对端口和 GPU PID。

## Migration Plan

1. 在 Mac 实现 v1.0.4、配置、测试工具和文档，不触碰既有路由函数。
2. 完成本地验证后同步到 server12，并以哈希确认两端代码一致。
3. 使用临时 GPU 配置启动单 Uvicorn worker，完成回归、容量和全量测试并生成报告。
4. 测试结束关闭 8084、释放本次 GPU 进程；v1.0.4 保持直连实验状态。
5. 回滚时停止服务并部署变更前提交；既有三个接口不需要数据或客户端迁移。

## Open Questions

- v1.0.4 的生产容量、单路纠正覆盖率和独立 GPU 下的收益必须由本 change 的 server12 测试确定，设计阶段不预设数值。
- 是否把 v1.0.4 接入 `online_gateway_service`、是否按多实例扩展到 50 路，留待本次容量报告完成后的独立 change 决策。
