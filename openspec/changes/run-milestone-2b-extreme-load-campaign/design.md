## Context

当前平台的当前权威拓扑为七类算子、21 个算子实例、四个可部署平台服务和三张 NVIDIA GPU：

```text
GPU0/1/2: asr_offline、asr_online、ocr、vbas、facerec、screen_det
CPU:      ppt_slice × 3
平台:    control-service、orchestrator-service、
          vision-orchestrator-service、online-gateway-service
基础设施: PostgreSQL、Kafka、Redis、MongoDB
```

Text Analysis 已退出当前平台；新 PPT 任务只执行 `PPT_SLICE -> PPT_OCR`，新 ASR 任务只执行 `ASR_TRANSCRIPTION`。A 服务只能通过 `192.168.29.11:18100` 提交/查询离线任务，通过 `192.168.29.11:18103` 请求在线图片、人脸库和实时 ASR；负载验证不得绕过平台直连算子。

现有 217 条反例和 26 条压力/恢复用例是功能和回归门禁，不是完整的 A 服务流量模型。现有压力证据尤其不足以估算长课程、在线多图、WebSocket、任务轮询和故障恢复同时出现时的真实上限。

目标服务器磁盘约 1.5 TB，已用约 93%，当前只剩约 103 GB；Docker 镜像和构建缓存存在大量可回收空间。因此实施必须先建立可审核的精确清理计划，再构建和压测；完成新版验收后还要精确退役上一版容器和镜像。

## Goals / Non-Goals

**Goals:**

- 得到一份可重放、可比较、可审计的 A 服务全栈极限负载结论，而不是只证明接口能响应。
- 分别测定控制面接收能力、任务排队能力、算子真实稳定吞吐、在线会话容量和过载恢复能力。
- 使用短媒体验证 100/300/1000 任务突发和调度吞吐，使用真实长视频验证 3/6/12/24/36 节课程的计算与存储边界。
- 验证在线图片最高 1000 并发、实时 ASR 最高 150 会话、任务查询最高 1000 QPS 下的有界过载行为。
- 在持续负载中验证单实例、单 GPU 实例组、平台服务、Kafka 和 Redis 的停止/重启恢复。
- 在不删除当前运行镜像、基础设施数据卷、`/data/result`、历史 release 报告和模型资产的前提下精确回收旧容器和旧镜像。

**Non-Goals:**

- 不修改 A 服务请求字段、HTTP/WebSocket 路径、任务状态、算子协议或四服务边界。
- 不把 `text_analysis` 重新纳入构建、部署、注册、路由或压测。
- 不以故意填满磁盘、打爆 PostgreSQL/Kafka 数据卷或中断整台主机作为“暴力压测”。
- 不使用宽泛 Docker prune、`docker compose down -v`、递归删除 `/data/course`、删除 `/data/result` 或改写历史 release。
- 不用性能报告替代 PPT、OCR、ASR 和视觉输出的 6 项 B 级人工质量复核。

## Decisions

### 1. 负载生成器与目标服务器分离

A 服务模拟器默认从 Mac 或另一台内网主机运行，不在 `192.168.29.11` 上生成主要负载。它只访问 `18100` 和 `18103`，并从 `192.168.29.12:5555/course/` 引用真实 T/S/P 视频。

这样可避免压测器抢占目标机 CPU/内存，也能把实际内网延迟、Base64 上传和 WebSocket 网络成本纳入结果。备选的“在目标机本地压接口”只作为定位网络差异的隔离探针，不作为最终容量结论。

在离线 Campaign 之前，必须先从 `192.168.29.11` 对
`192.168.29.12:5555` 执行 1/3/10/30 并发下载基线，同时记录单文件速度、总吞吐、建连耗时、失败率、源端文件服务资源和目标机入站网络。这份基线不绕过正式 URL 下载链路，只用于把媒体源/局域网上限与 Control、Orchestrator、ffmpeg 和算子耗时分开归因。如负载首先到达媒体源或网络上限，端到端结果仍照常保留，但不得用它推导 GPU/算子最大吞吐。

### 2. “提交并发”与“真实计算并发”分开

1000 个 `POST /api/course-jobs` 可以验证 Control、PostgreSQL、Outbox、Kafka 和 DAG 排队，但不能代表 1000 节长课程同时推理。Campaign 因此使用两套媒体：

| 数据集 | 目的 | 负载 |
| --- | --- | --- |
| 短片段 | 接口、幂等、Outbox、DAG、排队与快速排空 | 100/300/1000 唯一任务 |
| 45–60 分钟真实课程 | 下载、ffmpeg、算子、GPU、长租约、结果与磁盘 | 3/6/12/24/36 活动课程 |

不使用 100 节长课程一次性级联，因为它可能先消耗数百 GB 媒体空间，使返回的只是磁盘上限。如 36 节完成后仍有充足资源，更高阶梯必须作为新的显式配置和独立报告，不得在本计划中无界加压。

### 3. 七阶段 Campaign 固定顺序

```text
0 发布/资源预检 + 单请求基线
  ↓
1 单泳道阶梯
  ↓
2 A 端提交、幂等、优先级与查询突发
  ↓
3 在线图片 + 实时 ASR + 人脸库阶梯
  ↓
4 离线/在线混合负载
  ↓
5 过载 + 故障注入 + 恢复
  ↓
6 4/8 小时长稳 + 排空 + 精确清理
```

每个阶段都要生成独立起止标记、负载配置、随机种子、任务 ID 索引、原始指标和结论。前序阶段不符合时，后序可执行无依赖的定位探针，但最终结论必须为失败或阻断，不得跳过后写成通过。

### 4. 极限负载档位

#### 离线和查询

- 唯一 `task_id` 突发：100、300、1000。
- 同一 `task_id` 幂等突发：30、100、300、1000，覆盖相同请求和冲突媒体请求。
- 查询：50、100、300、1000 QPS，同时覆盖运行任务和已完成的大 ASR 结果。
- 真实长课：3、6、12、24、36 节，覆盖 PPT、ASR、教师行为、学生行为和四类混合 `task_types`。
- 优先级：先堆积 100/300 个 `NORMAL`，再插入 10/30 个 `URGENT`；只允许超越尚未领取的 `NORMAL`，不抢占已运行节点。

#### 在线图片与实时 ASR

- VBas、FaceRec、ScreenDet、OCR 分别执行 1/3/10/30/60/100/256/512/1000 并发，以 1080p、0.5–5 MiB Base64 为主数据。
- 在线图片混合比例默认为 VBas 60%、FaceRec 15%、ScreenDet 15%、OCR 10%，配置可覆盖。
- 多 S 流模拟 100/300/1000 路，每 5/10/30 秒一帧；1000 路、5 秒一帧等价于 200 RPS 持续 VBas 请求。
- ASR WebSocket 使用 1/10/24/30/60/90/150 会话，音频必须按真实采样速率发送；30 会话是当前三实例声明容量，60/90/150 用于验证过载。
- 人脸库使用 500/1000/5000 人数据集；新增、批量新增、查询、搜索和删除继续由 Online Gateway 固定转发到单一 FaceRec 管理实例，`/face/recognize` 才通过租约在三个 FaceRec 识别实例之间路由。报告分别给出单实例管理能力、三实例识别能力和共享 MongoDB 一致性，不声称管理请求已在三实例负载均衡。

Online Gateway 必须具备高于当前算子可调度容量的请求承接能力，不能继续由当前 `http.max_connections=100` 人为限制实测上限。参数继续通过 `online_gateway_service/config.toml` 调整；里程碑 2B 的三卡发布与压测配置使用 `max_connections=2048`、`max_keepalive_connections=512`，并保留有界 `pool_timeout_seconds`。这些参数是 Gateway 内部资源上限，不是业务容量声明。

Gateway 先通过 Control Service 申请租约：有可用算子容量时才使用出站连接，无容量时快速返回已定义的 `50301`。在 1000 并发常规图片用例中，不允许因 Gateway 连接池排队/超时产生 `50000` 或掩盖算子容量不足。最终报告必须分开 Gateway 承接吞吐、租约申请结果、各算子实测稳定吞吐和过载拒绝，并据此收敛后续 `declared_capacity`；不要求把 2048 连接全部发送给算子。

### 5. 混合档只定义入口负载，不伪造固定算法 SLA

| 档位 | 离线长课 | S 流 | 在线图片 | ASR WebSocket | 查询 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 日常 | 3 | 30路/10秒1帧 | 10并发 | 10 | 20 QPS |
| 高峰 | 12 | 100路/5秒1帧 | 100并发 | 30 | 100 QPS |
| 极限 | 36 | 300路/5秒1帧 | 1000并发 | 150 | 1000 QPS |

当前算子的推理耗时差异很大，`declared_capacity` 又是租约上限而不是实测吞吐，因此不在设计阶段虚构统一固定延迟 SLA。Campaign 先取得单请求和单泳道基线，再使用相对门槛判断目标负载：

- 在实测稳定容量内，非预期 HTTP 5xx/连接失败率不高于 0.1%，P95 不高于对应基线的 3 倍，P99 不高于 5 倍。
- 已接受离线任务在允许排队后必须进入预期终态；不得丢任务、重复节点或产生跨 `task_id` 结果。
- 超过稳定容量后，系统可以返回已定义的限流/过载结果，但必须快速结束、不返回未定义内部错误、不超卖租约，并在停止加压后恢复就绪。
- ASR 有效会话必须保持会话粘性和字幕隔离；声明容量内音频处理不得持续落后于真实时钟。
- 不允许 OOM、未预期容器重启、GPU 实例跨卡、无法排空的 Kafka lag/任务队列或持续泄漏的租约。

这些门槛是最低工程验收线，不改写用户后续确定的业务 SLA。

### 6. 故障注入必须受控且可恢复

故障注入使用精确 Compose 服务名或容器 ID，每次只执行一类故障：

1. 停止某一算子实例，等待 TTL 后验证剩余实例接管。
2. 停止单张 GPU 上的六个算子实例，验证剩余两卡的有界降级。
3. 逐个重启四平台服务；网关或 ASR 实例重启导致现有 WebSocket 中断时，验证客户端重连和租约回收，不声称无感会话迁移。
4. 分别受控重启 Kafka 和 Redis，验证 Outbox 重发、Consumer 恢复、注册 TTL 和租约最终一致性。

PostgreSQL 和 MongoDB 数据卷破坏、主机断电和网络防火墙全断不在本 Campaign 的自动故障注入内，因为它们需要独立的数据备份与灾备授权。

### 7. 资源护栏在负载生成器之上具有最高优先级

长稳和宿主机/GPU 资源至少每 5 秒采集一次；在线图片突发阶段对实例 `inflight`、活跃租约和容量峰值每 0.5–1 秒采集一次，并结合 Gateway 实例级请求、租约申请/拒绝/释放累计指标的阶段前后差值。不得因 5 秒时序快照未观测到短租约就判定未发生实例调度。以下条件中任一成立时，立即停止产生新负载、保留现场、执行精确恢复，但不删除证据：

- 宿主机剩余空间低于 100 GiB 或文件系统总容量的 10%。
- PostgreSQL、Kafka、Redis 或 MongoDB 数据目录所在文件系统低于相同红线。
- GPU Xid/ECC 严重错误、宿主机 OOM、容器连续重启、关键数据库不健康或发现跨卡 GPU 归属。
- 无法刷新容器/镜像账本、无法写入原子证据或维护锁所有权丢失。

警戒线设为剩余空间低于 15%或 150 GiB，到达警戒线时禁止进入下一阶梯，但可继续排空当前任务。

### 8. 镜像清理采用两阶段保护集差集

#### 构建前清理

1. 快照所有容器、完整镜像 ID、RepoTag/RepoDigest、Compose 身份和运行状态。
2. 保护所有运行容器引用的镜像、当前可回滚基线、本次必需基础镜像和人工允许列表。
3. 仅把不在保护集、无容器引用且明确属于旧版或悬空构建的完整镜像 ID 写入候选集。
4. 先发布 dry-run 计划，重新 inspect 确认无状态漂移后才逐 ID 删除。

精确镜像清理完成后必须先读取实际 `df`、`docker system df` 和 `docker buildx du`。如果镜像
已按计划删除，但 BuildKit 仍引用可重建层并导致磁盘未越过警戒线，可在用户对本次操作明确
授权后执行：

```bash
docker buildx prune --all --force --keep-storage 100GB
```

该命令只清理 BuildKit 缓存并保留 100 GB 最近缓存，不是镜像生命周期计划的替代品。执行前后
必须记录根盘、BuildKit 缓存、Docker 空间、镜像完整 ID 和运行容器状态；执行后还必须验证
缓存操作开始时的镜像集合零减少、当前发布/回滚/基础镜像仍存在、四平台和四中间件仍健康、
NVIDIA Runtime 与三张 GPU 仍可用。如果精确镜像清理结束到缓存操作开始之间发生外部状态
漂移，还必须单独记录其身份与时间边界，不能归因于缓存清理。没有逐次用户授权、
证据无法写入或执行后磁盘仍低于警戒线时继续失败关闭，不进入镜像构建。

#### 新版验收后清理

1. 只有新版 11 个镜像、21 个算子实例、四服务和必需负载阶段通过后，才能退役上一版。
2. 先把待退役停止容器的 `docker inspect`、镜像 digest、release 归属和停止状态写入不可变证据，再按完整容器 ID 删除这些旧容器。
3. 重新计算镜像候选集，只删除已无容器引用的上一版和更旧镜像。
4. 保留 PostgreSQL/Kafka/Redis/MongoDB 容器与数据卷、模型资产、`/data/result`、历史 release 报告和 Git 源码。

这一决策会降低无网络环境下快速回滚的便利性，但用户已明确要求清除旧镜像。回滚所需的镜像应通过对应 Git SHA 和外部模型基线重建，不通过无界保留本地旧镜像解决。

### 10. 部署手册必须由可执行事实驱动

交付文档固定为
`algorithm-scheduling-platform/deploy/算法功能调度平台部署手册.md`。它是面向部署人员的操作手册，不重复总体架构设计的推导过程，也不使用只能由开发者理解的隐式前提。手册至少包含：

1. 当前版本、拓扑、容器数量、GPU 布局、端口和网络边界。
2. x86_64、Docker/Compose、NVIDIA Runtime、磁盘、用户权限、目录、时钟和内网的前置检查。
3. Git SHA、七算子/四平台镜像标签、基础镜像和外部模型 manifest 的准备方式。
4. 七算子与四平台 `config.toml` 的实际路径、必需项、默认值和可调项；部署不使用 `.env`。
5. `/data/course/{task_id}`、`/data/result/{task_id}`、日志目录、报告目录和数据卷的建立、权限、留存与禁止删除边界。
6. 构建前精确清理 dry-run、基础设施启动、数据库迁移、四平台启动、21 算子启动、注册和 Smoke 的首次部署顺序。
7. `start-production-stack`、`status-production-stack`、`stop-production-stack` 的实际命令、工作目录、预期输出和失败处理。
8. A 服务对 `18100`/`18103` 的连通、离线提交/查询、在线图片和实时 ASR 最小验收。
9. 同 SHA 续跑、新 SHA 升级、失败回滚、已删旧镜像后的可重建回滚和验收后精确退役。
10. 日志查看、100 MiB 单文件轮转、7 日保留、健康/就绪、注册/租约、Kafka lag、GPU 与常见错误排查。
11. 部署前、部署后、升级后和清理后的可勾选验收清单。

手册中的命令不能凭手输复制出另一套逻辑。可执行步骤必须调用实际部署入口，并通过文档命令校验或在 `192.168.29.11` 的记录执行证明可用。这样手册不会在脚本演进后变成看似完整、实际无法交付的副本。

### 11. 迁移账本引入前的旧库按唯一连续前缀采纳

空库仍从 `0001` 开始顺序迁移。非空且账本为空时，迁移器在独立临时 schema
逐个重放当前迁移，只接受与旧库严格匹配的唯一 `0001`–`N` 前缀。既有账本先以同结构临时表核对列、
约束、索引、注释、owner/ACL 和访问方法。采纳时固定 `public` 边界，在同一事务内锁定平台表、
通过 `pg_class SHARE` 锁阻塞新关系对象，锁后要求其他事务与 prepared transaction 已排空；然后动态读取序列当前配置并原值重申以
取得序列关系锁，阻塞新的 `ALTER SEQUENCE`/`setval()` 而不用预扫描旧值覆盖漂移。在账本独占锁内再次核对 canonical 账本签名和
所有归属列 identity/serial 序列的下一键位置、上下界、cycle 和持久性，再核对表访问方法/表/列/约束/索引/序列/注释/权限/
RLS/触发器/策略/规则签名和必需数据不变量，然后才写入该前缀账本。随后仍通过普通迁移
执行 `N+1` 及后续版本。远端当前实际库对应 `0001`–`0006`，因此应先采纳 v6，再正常执行
`0007_retire_text_analysis_comments.sql`；不得把 v6 伪装为 v7 或重放 `0001`。

## Risks / Trade-offs

- [风险] 1000 提交与 36 长课可能产生大量 `/data/course` 临时文件。 → 短/长媒体分阶段，进入新阶梯前重新预估，低于 15%/150 GiB 禁止加压，低于 10%/100 GiB 立即停止。
- [风险] 在线 1000 并发可能先耗尽负载机的 socket/文件句柄。 → 记录负载机资源并支持分片 worker；结论必须区分负载机上限和被测系统上限。
- [风险] 三张 GPU 上同时运行六类模型可产生强烈的显存和算力争抢。 → 先做单泳道基线，再做混合阶梯，每 5 秒记录 GPU UUID、PID、进程归属、显存和利用率。
- [风险] 算法输出成功状态可能掩盖识别质量下降。 → 在每个泳道抽样核对结果结构和证据，保留现有 6 项 B 级人工复核为独立发布门禁。
- [风险] 删除旧容器/镜像会降低快速回滚能力。 → 只在新版通过后删除，删除前保存完整 inspect、digest、Git SHA 和模型基线，使旧版仍可重建。
- [风险] 清理 BuildKit 缓存会降低后续构建复用率。 → 仅在精确镜像删除后磁盘门禁仍未解除时逐次授权执行，并用 `--keep-storage 100GB` 保留最近缓存；镜像、容器、卷和持久数据不属于该例外。
- [风险] 部署手册与脚本、配置或实际端口漂移。 → 手册只引用权威入口，对关键命令做文档校验，并把最终远端执行证据绑定 Git SHA。
- [取舍] 极限档的预期会包含限流和快速拒绝。 → 本阶段的目标是确定安全边界和恢复能力，不是伪造“所有请求必须成功”的结论。

## Migration Plan

1. 完成 `standardize-service-file-logging` 和 `retire-text-analysis-from-scheduling-platform` 当前必需实现，将最终 clean Git SHA 作为本 Campaign 唯一版本键。
2. 实现可从独立主机运行的 A 服务模拟器、用例目录、负载配置、证据渲染器和资源护栏。
3. 实现 `start-production-stack`、`status-production-stack` 和 `stop-production-stack` 常驻入口，确保 Campaign 不复用结束时停止算子的 Canonical 验收入口。
4. 实现镜像/容器库存、保护集、dry-run、精确删除和原子证据；先用伪造 inventory 做单元测试。
5. 在 `192.168.29.11` 运行发布前预检和第一阶段旧镜像精确清理，将剩余空间提升到警戒线以上。
6. 同一 SHA 构建 11 个镜像，启动基础设施、四平台和21个算子实例，完成 revision、GPU、注册、租约和 7/7 Smoke 预检。
7. 按 0–6 阶段执行 Campaign，每阶段发布原始证据和中文结论；任一护栏触发即停止新负载并恢复。
8. 重跑 217 条反例、26 条压力/恢复用例和 6 项 B 级人工复核，确保新 Campaign 没有降低原有门禁。
9. 以已在目标机执行的命令和当前配置生成、校验中文部署手册，完成一次按手册从预检到 A 服务 Smoke 的独立复现。
10. 新版结论符合后，保存待退役容器证据，精确删除旧容器和旧镜像，验证新栈仍就绪并记录回收空间。

回滚时先停止新负载，恢复被注入停止的服务，保留 PostgreSQL、Kafka、Redis、MongoDB 和 `/data/result`。如旧镜像已在最终清理阶段删除，按记录的 Git SHA、Dockerfile、基础镜像和外部模型 manifest 重建，不改写已生成的 Campaign 证据。
