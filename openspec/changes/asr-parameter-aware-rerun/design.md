## Context

当前 `control_service` 在 `course_task_types` 上使用 `(task_id, task_type)` 唯一约束，并在首次创建时保存 `effective_params`。这能保证普通重复提交幂等，但无法支持同一课程先用一组 ASR 参数完成、之后再用另一组参数补充处理。

本变更只针对离线 ASR。ASR 算子现有 HTTP 接口和字段保持不变，平台负责把完整的 `effective_params` 传给算子。`task_id` 仍然是课程业务身份，不因为参数变化而创建新的课程。

## Goals / Non-Goals

**Goals:**

- 新 ASR 请求未传参数时，默认 `showSpk=false`、`showEmotion=false`、`showRoleIdentify=false`、`wordTimestamps=false`。
- 把参数规范化为完整快照并生成稳定指纹。
- 同一课程支持多个 ASR 参数执行版本，并能按参数版本查询结果。
- 相同参数的成功结果可复用；相同参数正在处理时不重复发布任务；未成功处理过的新参数可重新调度。
- 保留参数版本、运行状态和结果历史，保证并发提交下只有一个有效执行版本被创建。

**Non-Goals:**

- 不修改 ASR 算子的接口路径、请求字段或响应格式。
- 不把本次变更扩展到 PPT、OCR、VBas 或在线 ASR。
- 不提供无提示的“覆盖旧结果”行为。
- 不在本变更中设计通用人工重跑、取消或失败恢复接口。

## Decisions

### 1. 使用完整参数快照和指纹作为幂等键

请求进入 `control_service` 后，使用 Pydantic 模型补齐默认值，并按固定键排序、固定 JSON 编码生成 `params_fingerprint`。逻辑执行身份为：

```text
task_id + task_type(ASR) + params_fingerprint
```

不采用原始 JSON 字符串比较，因为字段顺序、缺省字段和空数组表达可能不同但语义相同。

### 2. 增加参数执行版本，而不是修改原任务参数

增加与 `course_task_types` 关联的执行版本记录（可命名为 `task_type_runs`），至少保存 `run_id`、`effective_params`、`params_fingerprint`、状态、原因、结果引用和时间字段。ASR 的 DAG 节点必须关联 `run_id`，这样不同参数版本可以顺序或并行存在，历史结果不会被覆盖。

已有非 ASR 任务继续使用现有逻辑；已有 ASR 记录迁移为一个初始执行版本，指纹由其已保存的 `effective_params` 计算。

### 3. 明确三种提交结果

- 找到相同指纹的成功执行版本：直接返回该版本的状态、`effective_params` 和结果。
- 找到相同指纹的活动执行版本：返回该版本的运行状态和 `run_id`，不新增 Outbox 事件。
- 没有相同指纹的成功或活动版本：在同一数据库事务中创建新执行版本、初始化该版本节点并写入一条 Outbox 事件。

失败、取消或结果不完整的版本不算“已处理成功”；后续相同参数请求可以创建新的执行版本。并发请求通过数据库唯一约束和行锁保证只有一个请求完成创建。

### 4. 查询按请求参数选择执行版本

提交接口在响应中返回选中的 `run_id` 和规范化后的 `effective_params`。查询接口在指定参数时返回该参数对应的执行版本；未指定参数时返回最近一次请求的版本，并同时列出该 ASR 的历史执行版本摘要，避免调用方误把另一组参数的结果当成当前结果。

### 5. Outbox 事件携带执行版本

ASR Outbox payload 增加 `run_id`、`params_fingerprint` 和 `effective_params`。`orchestrator_service` 按 `run_id` 初始化和推进节点，结果回写时同时更新执行版本和现有任务类型汇总状态。旧事件不携带 `run_id` 时仅按迁移兼容逻辑处理一次。

### 6. 保持算子兼容和默认值变更边界

默认值变更只对新建执行版本生效；数据库中已经保存的 `effective_params` 不被回写。算子仍接收显式的完整参数，因此算子无需了解“参数版本幂等”。

## Risks / Trade-offs

- [数据库模型扩大] 增加执行版本和按指纹查询会增加迁移及查询复杂度 → 先只让 ASR 使用执行版本，非 ASR 保持现有表和流程。
- [同一课程多版本并发占用算力] 参数变更可能导致旧版本和新版本同时运行 → 默认允许排队或串行策略，并在创建版本时记录关联状态；不允许静默覆盖。
- [结果响应变大] ASR 结果本身较长 → 结果继续存数据库，接口只返回结构化结果或已有结果引用，不把大段内容写入日志。
- [历史数据没有指纹] 旧 ASR 记录可能缺少规范化参数 → 迁移时按当前字段补默认值并计算指纹；无法确定的记录标记为需要重新处理，不直接宣称已完成。

## Migration Plan

1. 发布数据库迁移，增加执行版本表、`run_id` 关联、指纹索引和必要的中文字段注释。
2. 为已有 ASR 任务建立初始执行版本，使用其已保存参数计算指纹。
3. 先发布 `control_service`，确认新提交和查询能够识别版本。
4. 再发布 `orchestrator_service`，确认 Outbox 和节点执行都携带 `run_id`。
5. 运行默认值、重复提交、参数切换和并发提交测试。
6. 回滚时停止新版本创建，继续读取已有任务；已经创建的执行版本保留，不删除历史结果。

## Open Questions

- 查询接口是否需要提供“按参数提交并立即返回该版本”的显式字段名，还是沿用现有 `asr_options` 并在响应中增加 `run_id`。
- 同一课程的不同 ASR 参数版本是否允许同时占用算子容量，还是必须等待前一个版本进入终态。
