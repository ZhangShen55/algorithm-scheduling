## 现状与约束

最近一轮 8 个全量课程任务共向三台 VBas 下发 1328 个 batch，实例分配为 `456/427/445`，说明路由基本均衡；但 VBas 活跃窗口内三实例同时空闲约 53.9%，平均活跃请求仅 `0.70/6`，容量申请失败仅 `3/1328` 且均首次重试成功。现有链路同时包含 Kafka 消费、课程级视觉命令、视频探测、FFmpeg 抽帧、ready queue、Control 租约和 VBas HTTP 调用，因此只能判断供料不足的嫌疑很高，不能据此宣称 VBas 已达到硬件上限。

本次验证运行在 `192.168.29.11`，使用三张 GPU 和三个 VBas 实例。测试必须保持同一镜像 revision、模型、GPU 拓扑、固定教师/学生图片语料和固定视频。VBas 现有 HTTP 合同、A 服务合同、模型输出和视觉聚合规则均不可因基准测试改变。

## 目标与非目标

**目标：**

- 在上游始终有足量已准备帧的前提下，得到教师、学生及混合负载的 VBas 单实例和三实例稳定吞吐。
- 从受控高并发向下搜索，找到最高稳定吞吐对应的并发区间及较低资源拐点。
- 将“显存首次加载或缓存平台上升”与“随请求持续膨胀”分开，给出可复核的稳定性结论。
- 分别测量媒体供料、租约分发和完整链路，明确 VBas 空档来自抽帧、命令启动、租约还是 HTTP 分发。
- 输出可以直接用于 `MaxConcurrentOfflineBatches`、Vision 课程并发、媒体并发和预取配置的量化建议。

**非目标：**

- 不在本变更中改变模型、精度、批次业务含义、接口字段或响应结构。
- 不把 FFmpeg 进程数预先限制为 CPU 核数；VBas 裸能力阶段完全绕过 FFmpeg，媒体阶段允许主机充分竞争 CPU 并以实测吞吐判断是否过度调度。
- 不在得到隔离基准前直接提高生产容量声明，也不把一次短时峰值当作稳定容量。
- 不用未完成的完整链路测试替代 VBas 裸能力结论。

## 技术决策

### 1. VBas 基准使用预生成帧和同机持续供料器

从真实教师、学生视频抽取并冻结一组 JPEG，记录文件数量、尺寸分布和 SHA-256。请求体在计时前生成，图片位于三个 VBas 容器均可读取的共享路径；负载器运行在目标服务器，按实例地址直连现有 VBas 接口，从而排除媒体下载、FFmpeg、Kafka、Control 租约和外部网络。

负载器保持每个目标实例的待执行请求数达到当前测试并发，上一请求完成后立即补位。供料器自身 CPU、事件循环和连接池必须留有余量；若客户端发送端不能维持目标并发，本轮标记为供料器受限，不得归因于 VBas。

选择预生成帧而不是无限放大 FFmpeg，是因为本阶段只回答 VBas 在“有货可取”时的能力。这样 FFmpeg 不设上限也不会污染 VBas 基准；FFmpeg 的实际供料上限在独立阶段测量。

### 2. 使用高位起测、阶梯下降和拐点复测

默认单实例离线并发阶梯为 `8 -> 6 -> 4 -> 3 -> 2 -> 1`，允许 Harness 配置更高的受控测试上界。这里的上界不是配置字段可接受的理论最大值，而是根据 GPU 总显存、已知历史运行和停止护栏确定的本轮极限。三实例同时执行时总并发对应为 `24 -> 18 -> 12 -> 9 -> 6 -> 3`。

每档均重启 VBas 以恢复相同基线，完成模型就绪、固定预热和不少于 10 分钟或 10,000 batch 的稳态采样。教师、学生先分别执行，再按固定 50%/50% 序列执行混合负载。出现 OOM、容器重启、错误率超限、显存越过硬护栏或延迟持续恶化时立即停止该档，保留失败事实并进入下一低档。

最高稳定吞吐档用于描述性能极限；在其吞吐 95% 以内的最低并发档定义为推荐拐点。二者都报告，不用一个“最优值”掩盖性能和资源之间的差别。

### 3. 显存稳定以平台期而不是绝对不增长判定

GPU 框架首次推理和缓存分配允许显存从模型就绪基线升到新的平台。每档记录 `M_ready`、预热结束的 `M_warm`、稳态 P50/P95/峰值、最后五分钟趋势和测试结束值。以下任一情况视为持续膨胀：

- 稳态后显存仍呈持续正向趋势，最后窗口没有形成平台；
- 相同负载的后半段显存分布持续高于前半段且超过配置化容差；
- 达到 GPU 显存硬护栏、出现 OOM、容器重启或推理分配失败。

最终报告必须同时给出原始时间序列和判断阈值。单纯从约 1.5 GiB 上升到稳定的 4–5 GiB 不自动判为泄漏；是否接受该平台由吞吐、显存余量和长稳结果共同决定。

### 4. 媒体供料阶段取消应用层人为瓶颈

纯媒体阶段执行真实视频探测和抽帧，但把准备好的 batch 写入零延迟 sink，不申请租约、不调用 VBas。测试时将媒体槽位配置为不小于活动视觉流数量，确保应用层 Semaphore 不先成为上限；允许 FFmpeg 使用主机可调度的 CPU 和内存。由于当前 FFmpeg 命令未设置 `-threads`，报告必须记录实际进程数、线程数、CPU、load average、iowait 和 `prepared batch/s`，而不能用“进程数等于核数”推导能力。

活动视觉流从高位开始下降，默认 `16 -> 12 -> 8 -> 6 -> 4 -> 2 -> 1`。当降低活动流后吞吐上升，说明高位存在 CPU、磁盘或进程争用；当吞吐基本不变而资源下降时，较低档为媒体推荐拐点。

### 5. 预抽帧回放隔离租约和分发

预先准备完整 batch 后，恢复 Vision 的 VBas 客户端、Control `offline` 租约、实例选择和真实 HTTP 调用，但禁止该轮再启动 FFmpeg。每个 batch 记录以下单调时钟：

```text
frame_batch_ready_at
lease_requested_at
lease_acquired_at
vbas_started_at
vbas_finished_at
```

由此分解 `ready -> lease`、`lease -> HTTP start` 和 VBas 服务时间。若 ready queue 至少有六个 batch，但仍有 VBas 离线槽位空闲，归因为租约或分发；若 ready queue 不足六个，则归因为供料。容量快照等待和权威租约拒绝必须分开统计。

### 6. 完整链路只使用隔离阶段选出的候选参数

完整链路使用相同课程、相同 task 数和全新 `task_id`。先运行当前配置作为 D0，再只替换一个变量或一组具有直接依赖的变量，禁止同时任意改变全部参数。至少对照课程 Consumer 拉取、课程级并发、媒体活动流和 batch 预取，并验证：

- 三实例同时空闲比例；
- 平均活跃离线槽位和六槽同时占用时间；
- ready queue 为空和非空状态下的空档时长；
- 首批准备、批间隔、租约等待、VBas 请求和视觉终态耗时；
- 成功率、显存平台、容器重启、Consumer 健康和临时文件清理。

“VBas 连续处理”定义为 ready queue 有足量 batch 时空闲槽位能在目标时间内补位，而不是要求某个实例在无待处理数据时也保持忙碌。

### 7. 证据写入 Harness 且失败不可覆盖

每次执行生成独立 `campaign_id`、随机种子、Git SHA、镜像 ID、有效配置、fixture manifest、开始结束时间、退出码和原始指标路径。中断、护栏停止、客户端供料不足或缺失时间序列均保留为未通过，不得从后续平台排空事实补写成功。

隔离阶段和完整链路报告分别给出事实、计算过程和结论。最终配置建议必须可追溯到至少两轮重复结果，重复吞吐偏差默认不超过 5%。

## 风险与权衡

- [从高并发开始可能快速耗尽显存] -> 设置显存硬护栏、OOM/重启监控和自动停档；每档重启实例，失败档不继续延长。
- [负载器先达到瓶颈] -> 同机运行、预构造请求、监控客户端事件循环和连接池；不能维持目标并发时使用例失败关闭。
- [PyTorch 缓存被误判为泄漏] -> 区分 ready、warm 和 steady 三个阶段，并检查长稳趋势而非只比较起止值。
- [媒体阶段不限制 FFmpeg 导致过度调度] -> 这是发现主机极限的一部分；以实际吞吐下降和资源争用确定拐点，不把最高进程数直接作为生产建议。
- [教师和学生模型成本不同] -> 分项基准后再做固定比例混合测试，不用单一图片代表全部视觉工作。
- [完整链路变量过多导致归因失真] -> 先完成三个隔离阶段，完整链路每轮只改变一个因素并复用固定 fixture。

## 实施与回滚

1. 固化现有服务器 revision、镜像、容器、有效配置和三卡显存基线。
2. 准备固定教师/学生帧语料与 manifest，完成负载器自测。
3. 执行 VBas 高位到低位能力阶梯，生成吞吐和显存曲线。
4. 执行无 VBas 的媒体供料阶梯，再执行预抽帧租约分发回放。
5. 计算性能极限档和 95% 吞吐推荐拐点，重复两轮验证。
6. 将候选参数应用到完整视觉链路并执行对照回验。
7. 若实现新增测试指标或测试接入点，仅缓存构建实际受影响镜像；新容器通过 revision、health 和 readiness 后再精确删除被替换的旧容器和旧镜像。
8. 任一部署门禁失败时恢复原镜像和配置；基准数据保持只读，不因回滚删除。
