# v1.0.3 渐进纠正与并发容量报告

## 结论

- 推荐生产配置：Uvicorn worker 固定为 `1`，`sensevoice_correction_workers = 1`，单实例最多承载 `4` 路实时会话。
- `1/2/4/6` 个 correction worker 的最大通过并发均为 `4`，首个失败并发均为 `8`，且两侧复验结果一致。
- 增加 correction worker 没有提高容量上限。并发 `8` 时 partial p95 为 `20.64-23.18 s`，主要瓶颈是单实例在线 ASR 的受控串行入口和事件循环调度，不是 SenseVoice 队列。
- worker 从 `1` 增至 `6` 时，并发 `4` 的 GPU 显存峰值从 `3051 MiB` 增至 `7939 MiB`，没有容量收益，不建议用更多模型副本换取吞吐。
- v1.0.3 的请求路径和 `key/text/finished/bg/ed` 响应字段未变；`finished=true` 仍只表示字幕段结束，中间纠正保持同 key、`finished=false`。

## 测试环境与口径

- 服务器：`server12`，3 张 RTX 4090，本次服务使用 `cuda:0`。
- 服务：单 Uvicorn worker，客户端在服务器本机连接 `127.0.0.1:8084`。
- 音频：`教师1_16k.wav`，16 kHz、单声道、16-bit PCM，每块 `0.48 s`。
- 矩阵：correction worker=`1/2/4/6`，并发=`1/2/4/8/16/32/64`，每点从 98 秒处连续发送 600 秒。
- 实时通过要求：全部客户端发送完成，partial/中间纠正/finished p95 分别不超过 `1.0/1.0/1.5 s`，RTF 不超过 1，无 OOM、协议或时间轴错误、异常关闭和队列过载。
- 表中延迟均为秒，格式为 `p50/p95/p99`；`S/D/T/F` 分别为 stale、degraded、final timeout、queue full。
- 失败点被 watchdog 提前终止，旧版工具按计划音频计算的 RTF 偏低，因此失败点 RTF 仅保留原始值，不用于容量判断。工具已改为后续按实际发送音频计算。

## 压测工具修正

首次矩阵从 worker=1 切换到 worker=2 时，旧服务在退出窗口仍能返回 `/get_status`，工具误认为新进程就绪，导致 worker=2/6 点被错误记录为 `ConnectionRefused`。修正后就绪条件同时要求：

1. `/get_status` 连续两次返回 200；
2. 8084 监听 PID 属于本次启动的进程组。

worker=2/6 的 14 个点和边界已在修正后全部重跑，上表采用重跑结果。工具还改为按实际发送音频计算提前失败点 RTF，并增加队列深度和在途任务平均值，避免后续报告误读。
