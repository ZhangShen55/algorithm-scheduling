## Context（背景）

v1.0.3 目前与 v1.0.2 共用 `_run_revision_session()`，在线模型持续返回临时文本，SenseVoice 只在 `finalize_segment()` 中对整段 PCM 执行一次。VAD 候选 end 最长等待 720 ms，单段最长约 20.16 秒，因此长句在最终完成前没有 SenseVoice 的纠正和标点。

模型当前为进程级单例，多个会话通过 `asyncio.to_thread()` 直接并发调用同一实例。该方式既没有线程安全约束，也没有队列长度、背压、超时和过期结果控制；历史并发测试出现过共享在线模型长时间无响应。新方案必须保持已有 WebSocket 合同，并以 `server12` GPU 实测确定容量，而不能把单路模型耗时直接外推为并发能力。

## Goals / Non-Goals（目标与非目标）

**Goals（目标）:**

- v1.0.3 在 `finished=true` 前返回同 `key`、`finished=false` 的 SenseVoice 中间纠正文本。
- `finished=true` 继续只表示字幕段真正结束，不由一次中间纠正或一次 VAD 事件直接决定。
- 中间纠正调用量有界，旧 revision 不能覆盖更新的在线文本或新 revision。
- SenseVoice 并发调用具有明确的模型所有权、有界队列、优先级、超时和释放语义。
- 通过 28 组 worker/会话并发矩阵给出可复现的实时容量结论。

**Non-Goals（非目标）:**

- 不改变 v1.0.1、v1.0.2、`online_gateway_service` 或上游 0.48 秒分块方式。
- 不增加或删除 WebSocket 请求字段及 `key/text/finished/bg/ed` 响应字段。
- 不承诺 64 路一定达到实时；测试必须如实记录首个不满足实时标准的边界。
- 本次不引入新的 ASR/VAD/标点模型，不让 v1.0.3 重新依赖独立标点模型。
- 不把纠正 worker 数解释为 Uvicorn worker 数；压测期间 Uvicorn 固定为 1。

## Decisions（技术决策）

### 1. 将字幕完成状态与纠正 revision 分离

每个 v1.0.3 会话维护单调递增的 `revision_id`、当前 `segment_key`、PCM 样本边界、最后已接受纠正边界和最后发送文本。纠正快照包含 `connection_id`、`segment_key`、`revision_id`、`start_sample`、`end_sample`、PCM 副本和任务类型。

SenseVoice 返回后，只有任务仍属于当前连接和当前 `segment_key`，且 revision 和样本边界不落后时才允许发送。中间结果使用快照时的 `bg/ed` 和 `finished=false`；VAD 候选超时、超过最大段长或连接结束流程仍是唯一的 `finished=true` 来源。

备选方案是给响应增加 `revision` 或 `source` 字段，但这会改变客户端合同，因此不采用。

### 2. 使用复合触发条件而不是每块或每个字都纠正

默认触发顺序如下：

1. VAD 产生新的候选 end 时立即提交一次中间纠正快照。
2. 连续长语音没有候选 end 时，自上次已提交快照起稳定文本累计新增 8 个字符，且距离上次提交至少 2 秒，则提交快照。
3. 即使稳定文本未增加 8 字，累计新增音频达到 4.8 秒且不在冷却期，也提交快照，防止慢语速长时间不纠正。
4. 相同 `segment_key` 和 `end_sample` 不重复提交；文本没有实际变化时不重复发送。

字符阈值、音频上限和冷却时间进入配置，默认分别为 `8`、`4800 ms` 和 `2000 ms`。单独使用“每新增 8 字立即纠正”会在快速语音下产生过多重识别，因此字符阈值必须同时受冷却和在途限制约束。

### 3. 每会话一个在途任务，待处理快照 latest-only

一个会话最多有一个 SenseVoice 任务在队列中或执行中。任务在途期间出现的新触发只替换该会话的 pending 快照，不追加多个任务。当前任务完成后，如果 pending 边界更新且仍有效，只提交最新快照。

VAD 候选 end 的中间结果如果与最终边界完全一致，finalize 复用该结果发送 `finished=true`，不再次调用 SenseVoice；如果候选窗口内出现新语音，则旧结果最多作为中间显示，后续 revision 使用合并后的完整 PCM。

### 4. 使用有界优先队列和独占模型 worker

新增进程级 correction scheduler。配置的每个 SenseVoice worker 独占一个模型实例，不允许多个线程同时调用同一实例。队列区分 final 与 intermediate：final 优先；intermediate 在队列满时允许被同会话新快照覆盖或跳过，不能阻塞在线 ASR/VAD 主循环。

final 任务必须有界等待；超时或推理失败时使用当前最新可见文本执行完成流程，并记录降级原因。这样故障不会让字幕永久停留在 `finished=false`。默认队列容量按 worker 数设置一个保守倍数，具体值在实现时配置并由压测验证。

worker 模型在服务启动阶段完成加载，只有全部配置实例可用后服务才进入就绪状态。GPU OOM、模型加载失败或非法 worker 数必须导致明确的启动失败和日志，不得静默减少 worker 数。关闭服务时停止接单、取消未开始任务、等待或超时终止在途任务并释放模型引用和 CUDA cache。

备选方案是多个 worker 共享一个 SenseVoice 单例，但 FunASR `AutoModel` 的并发线程安全没有保证，因此不采用。动态 micro-batch 可作为后续优化，本次先获得独立实例的真实容量基线。

### 5. v1.0.3 对共享在线 ASR/VAD 调用增加受控入口

v1.0.3 的并发会话不得继续无约束地从多个 `to_thread` 同时调用同一在线 ASR 或 VAD 实例。实现应通过各模型独立的进程级异步锁或单消费者执行入口保护调用，并记录排队和执行时间。锁不能跨 WebSocket 网络发送或 SenseVoice 纠正等待持有。

该约束首先保证模型状态不会因并发调用损坏；若串行入口成为容量瓶颈，报告必须明确指出，不能用增加 SenseVoice worker 掩盖。v1.0.1/v1.0.2 行为不在本次修改范围。

### 6. 所有出站响应由会话事件循环顺序发送

worker 只解析并返回纠正结果，不直接操作 WebSocket。会话循环消费完成通知、校验 revision 后调用现有 `send_result()`，从而保证同一连接响应顺序、`bg/ed` 单调和断开后的零发送。连接断开时标记会话失效，删除 pending 快照；已经在线程中执行的推理结果返回后直接丢弃。

内部结构化日志只记录 worker、触发类型、revision、样本边界、排队/推理耗时、队列深度、丢弃和降级原因，不记录完整音频或完整识别文本。

### 7. 使用真实节奏、分层时长和硬 watchdog 的远端压测

压测在 `server12` 本机发起，连接 `127.0.0.1:8084`，避免 Mac 网络和 Tailscale 影响。每个 worker 配置重启一次 Uvicorn，等待模型全部加载；启动最长等待 10 分钟，通常至少预留 5 分钟。若配置因 OOM 无法启动，该 worker 行直接记为不可用，不继续无意义等待。

测试分三层：

- 正确性基线：worker=1、并发=1 使用 47 分钟完整 `教师1_16k.wav`，与现有 v1.0.3 C 结果比较时间轴、完成段和纠正次数。
- 容量矩阵：worker=`1/2/4/6` × 并发=`1/2/4/8/16/32/64`，每点使用教师音频连续 10 分钟、每 0.48 秒发送一块，连接起始错开 0 至 480 ms；发送结束后最多等待 30 秒排空。
- 边界复验：每种 worker 数下选取“最大通过并发”和“首个失败并发”，重复一次；最终推荐配置再执行一次完整教师音频稳定性验证。

首响应超过 10 秒、任一活跃连接连续 15 秒无响应、进程退出、CUDA OOM、队列/端到端积压连续 30 秒增长且超过 60 秒，均触发该点提前失败并保留诊断信息。单点硬超时为发送时长加 90 秒。

### 8. 实时判定和报告口径固定

一个矩阵点只有同时满足以下条件才标记“实时通过”：

- 所有连接完成规定音频发送，无 stalled、异常关闭或进程重启。
- 输入音频时钟相对墙钟的最终积压不持续增长，整体 `RTF <= 1.0`。
- 普通 partial 响应延迟 p95 不超过 1.0 秒。
- 中间纠正从触发到可见的延迟 p95 不超过 1.0 秒。
- 最终 `finished=true` 在确认边界后的延迟 p95 不超过 1.5 秒。
- 测试结束前纠正队列可回落，无 CUDA OOM、时间戳倒退、跨 key 覆盖、重复 final 或协议字段异常。

报告同时给出 p50/p95/p99，而不是只给平均值。原始 JSONL、资源采样和服务日志保存在 `asr_online/test/` 的忽略目录；汇总结论写入本 change 的 `benchmark-report.md`。

## Risks / Trade-offs（风险与取舍）

- [风险] 多个 SenseVoice 实例使 `4/6` worker 超出 GPU 显存。→ 启动阶段显式失败并记录峰值显存；报告将该配置标记为不可部署，不自动降级。
- [风险] 中间纠正会重复处理逐渐增长的 PCM，算力随句长增加。→ 使用复合阈值、2 秒冷却、latest-only 和 20.16 秒硬切段限制调用量。
- [风险] 在线 ASR/VAD 串行保护可能先于纠正池达到瓶颈。→ 分别记录模型排队耗时，在报告中按阶段归因，后续再决定是否实现安全 micro-batch 或模型副本。
- [风险] worker 返回顺序与在线 partial 顺序不同。→ revision 与样本边界双重校验，只有会话事件循环发送。
- [风险] SenseVoice 中间文本可能相对在线文本发生明显跳变。→ 只在有实际文本变化时发送，保持同 key 替换语义，并在完整教师音频中统计文本回退和重复。
- [风险] 28 点矩阵耗时较长。→ 固定 10 分钟稳态窗口并允许明确故障提前停止；不得缩短通过点来制造更好的结果。

## Migration Plan（迁移与回滚）

1. 在 Mac `asr` 环境实现配置校验、scheduler、v1.0.3 会话状态和单元测试，验证 v1.0.1/v1.0.2 协议测试不变。
2. 增加压测客户端、资源采样和报告汇总工具，先用短音频验证 watchdog 与指标计算。
3. 提交推送后同步到 `server12:/root/workspace/asr_online`，保持 Uvicorn 单进程并按 worker 配置依次重启。
4. 完成正确性全量测试、28 点矩阵和边界复验，生成 `benchmark-report.md`。
5. 测试结束后关闭 8084，确认端口、后台进程和 GPU 计算进程均已释放。
6. 若中间纠正导致稳定性或质量回退，可通过配置关闭中间触发，恢复 v1.0.3 仅句末纠正；协议无需回滚。

## Open Questions（待实测结论）

- `server12` 的可用显存最多能稳定加载多少个 SenseVoice 实例。
- 受控在线 ASR/VAD 入口在何种并发下成为主要排队来源，是否值得后续增加模型副本或 micro-batch。
- 默认 8 字、4.8 秒、2 秒冷却在完整教师音频上的纠正收益与额外调用量是否达到合理平衡。
