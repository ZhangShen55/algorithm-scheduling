## Why

2026-09-03 的 20 路全量课程与在线人数识别 200 并发、10000 次混合压力验证发现：Control Service
短暂替换会让 Vision 的容量租约连接异常直接终止长时间视觉节点；Online Gateway 又会把容量等待、
平台连接和算子调用等不同失败混为少数业务错误并立即返回 A 服务。当前行为无法满足“容量不足时
在平台内部等待、瞬时故障可恢复、超过明确总时限才失败”的调度目标，也无法支持可信的交付压测。

## What Changes

- 为 Vision 离线批次租约申请增加有总时限的瞬时连接错误和可恢复服务错误重试；重试期间节点保持
  运行态，确定性错误快速失败，租约和 VBas 批次仍保持幂等。
- 为 Online Gateway 建立覆盖容量等待、Control 调用、VBas 调用和有限重试的单一请求时间预算；
  容量不足不直接返回 A 服务，可恢复错误在预算内重试并重新选择实例。
- 明确 VBas 在线容量与内部队列边界：平台按每实例在线处理容量发放租约，未取得租约的请求留在
  Gateway 等待；内部队列只作为瞬时竞争和直接调用的兜底，不把 200 并发简单计算成算子过载。
- 细分容量等待超时、Control 持续不可用、VBas 连接或协议失败、VBas 响应超时和未分类内部错误；
  保持 HTTP 200 加业务码的既有北向响应方式，参数错误不重试。
- 补充结构化日志和指标，使每个失败能够按阶段、异常类型、实例、重试次数和耗时归因，同时禁止
  记录 Base64、完整请求体或识别结果。
- 在 `192.168.29.11` 利用既有构建缓存重新构建和替换受影响镜像；新容器健康后精确删除被替换的
  旧容器和旧镜像，不执行宽泛镜像或构建缓存清理。
- 执行多轮在线、离线和混合并发压力测试，持续采集任务终态、租约、Kafka/Outbox、三台 VBas
  分布、GPU 显存与利用率、临时媒体清理和持久结果保留。
- 将“全部请求和课程任务达到终态、队列与租约收敛、证据完整”设为出具结论的前置条件；未完成、
  服务版本中途变化或证据缺失的测试只能记录为中断或环境失效，不能给出通过结论。
- 显存若相对稳定基线持续增长，必须停止扩大负载，完成请求阶段、接口、实例和内存释放行为归因，
  修复并重新从冷启动基线执行该轮测试。

## Capabilities

### New Capabilities

- `capacity-wait-recovery`: 规定 Vision 离线租约和 Online Gateway 在线请求的有界等待、瞬时故障
  恢复、错误分类、幂等与可观测行为。
- `mixed-load-release-validation`: 规定服务器缓存构建、精确替换清理、多轮并发压力、GPU 显存监控、
  文件生命周期和完整终态验收门禁。

### Modified Capabilities

无。

## Impact

- 主要代码：`vision_orchestrator_service`、`online_gateway_service`，以及必要的共享租约恢复工具、
  配置模型、测试和日志指标。
- 运行依赖：`control_service` 的现有租约接口、Redis 注册与租约状态、Kafka、PostgreSQL、三台 VBas
  实例；本变更不改变四服务边界。
- 北向接口：保留现有路径、方法、请求和成功响应；失败仍使用 HTTP 200 加业务码，但错误码语义更
  精确。若调用方希望等待平台完成重试，其客户端超时必须大于 Gateway 的总请求预算和网络余量。
- 部署：只构建和替换实际受代码影响的服务镜像；若共享包变动导致其他镜像源码内容变化，须根据
  镜像依赖关系扩大构建范围并记录原因。
- 验证证据：OpenSpec 任务、中文 Harness 场景、服务器原始 write-once 报告和 Git 提交历史。
