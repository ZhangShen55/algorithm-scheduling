## Context

当前调度平台将 VBas 容量拆成离线与在线两个池。`192.168.29.11` 上有三个 VBas 实例，当前每实例
在线处理容量为 24、在线内部队列为 24、离线批次容量为 1。Control Service 根据注册容量发放租约，
Vision Orchestrator 取得离线租约后发送行为分析批次，Online Gateway 取得在线租约后转发单图请求。

2026-09-03 的混合压力验证暴露了两个独立问题：Vision 的租约申请只等待容量不足，对 Control
短时连接失败立即终止节点；Online Gateway 虽已等待容量，但连接、续租、算子调用和响应解析错误
分类不足，116/10000 个请求只得到笼统错误，无法证明是容量过载。测试过程中发生服务替换还说明
正式验收必须锁定运行版本，并以全部业务、队列、租约和文件达到终态作为结论前提。

本设计不依赖 Kubernetes。PostgreSQL、Kafka、Redis、共享 `/data/course` 与 `/data/result` 以及
现有四服务边界保持不变。

## Goals / Non-Goals

**Goals:**

- Control 短时不可达或返回可恢复服务错误时，Vision 离线批次在明确预算内恢复，不直接损失长时间任务。
- 在线容量不足和可恢复调用失败由 Gateway 等待或有限重试，正常压力只增加延迟，不立即向 A 服务报错。
- 每个在线请求只有一个端到端时间预算，容量等待、连接、推理和重试不能叠加成无界等待。
- 外部业务错误能够区分容量耗尽、Control 不可用、VBas 连接或协议失败、VBas 响应超时和未知错误。
- 通过固定版本、多轮真实压力、故障注入、GPU 显存和文件生命周期证据验证修复。

**Non-Goals:**

- 不调整 VBas 模型、推理精度、`MaxConcurrentOnlineRequests=24` 或 `MaxQueueOnlineSize=24` 的默认值。
- 不把 VBas 内部在线队列纳入 Control 可发放租约容量，也不允许 Gateway 绕过 Control 直接选实例。
- 不引入 Kubernetes、服务网格或本轮实现 Control 多副本高可用。
- 不改变在线接口路径、请求字段、成功响应或 HTTP 200 加业务码的北向响应形式。
- 不以无限等待保证永不失败；总预算耗尽、确定性请求错误和不可恢复协议错误仍必须形成终态错误。
- 不以本变更处理服务器总体磁盘容量规划问题，但必须验证本轮临时文件能够及时清理。

## Decisions

### 1. 统一可恢复错误分类，但保留在线与离线调用边界

租约客户端 SHALL 将结果区分为：

- `capacity_unavailable`：Control 明确返回没有目标容量，继续等待。
- `control_transient_failure`：连接错误、连接超时或 HTTP 502/503/504，在预算内重试。
- `control_deterministic_failure`：HTTP 400/401/403/404/409 等确定性错误，立即失败。
- `invalid_control_response`：租约响应缺少必要字段或类型错误，立即失败并保留脱敏上下文。

Vision 与 Online Gateway 可复用退避和异常分类工具，但各自持有调用上下文、日志字段和最终业务语义，
不把两个服务合成一个运行组件。选择有限重试而不是立即失败，是因为注册与租约事实位于 Redis，
Control 进程短时替换不会使事实丢失；选择有界而不是无限重试，是为了避免 Kafka 消费者和 HTTP 连接
永久占用。

### 2. Vision 节点在租约恢复期间保持运行态

Vision 使用现有 `acquire_wait_timeout_seconds` 作为单次视觉批次租约申请的累计预算，默认 300 秒。
退避从现有 `acquire_retry_interval_seconds` 开始，按倍数增加并在 2 秒封顶，同时增加随机抖动。
容量不足和 Control 瞬时故障均消耗同一预算。

重试只发生在租约申请阶段；未取得租约不得调用 VBas。取得租约后继续使用稳定的 `task_id`、
`batch_id` 和帧摘要，确保 Control 恢复不会产生新的逻辑工作。重试期间节点维持状态 50，只有预算
耗尽或确定性错误才进入状态 70，并继续使用既有视觉失败终态事件通知 Orchestrator。

替代方案是把 Kafka 消息退回后整体重放。该方案会扩大命令代次、重复初始化和状态竞争面，因此本轮
选择在批次租约边界内恢复；进程崩溃时仍由现有 Kafka 重放机制兜底。

### 3. Online Gateway 使用单一端到端截止时间

保留 `[http].hard_timeout_seconds=600`，但把它定义为在线 HTTP 请求从进入 Gateway 到生成响应的
端到端总预算，而不是只包裹某一次 VBas 调用。容量等待、Control 重试、VBas 重选和 VBas 调用均从
同一个 monotonic deadline 计算剩余时间。

`[leases].acquire_wait_timeout_seconds=300` 是累计容量等待上限，同时受剩余总预算约束。每次 VBas
调用的连接、写入和读取超时不得超过剩余总预算；现有固定 `read_timeout_seconds=60` 不得在仍有预算
且允许重试的情况下直接形成最终错误。A 服务的客户端超时应配置为至少 630 至 660 秒，以覆盖
Gateway 的 600 秒预算和网络余量，但增加 A 服务超时本身不能替代 Gateway 内部修复。

选择统一截止时间而不是为每次尝试重新计时，可防止三次重试把 600 秒放大成 1800 秒。上游取消连接
时，Gateway 必须取消等待或下游调用并释放已取得租约。

### 4. 平台在线容量不包含 VBas 内部等待队列

每实例向 Control 注册的 online pool 容量继续等于 `MaxConcurrentOnlineRequests=24`，不加上
`MaxQueueOnlineSize=24`。因此三个实例最多同时持有 72 个平台在线租约；200 个并发请求中其余请求
在 Gateway 等待容量释放。VBas 内部最多 24 个等待项只用于容量快照延迟、瞬时竞争或绕开平台的
直接调用保护，不能作为 Gateway 继续超发的依据。

如果 VBas 仍返回 429/503，Gateway 释放当前租约，把该次结果记录为可恢复的实例拒绝，重新申请
租约并优先避免立即选择同一实例。该行为可以吸收注册快照与实例内部准入的瞬时差异。

### 5. 在线纯推理允许有限重试和实例重选

人数、教师和学生在线图片接口均为无持久副作用的同步推理。以下错误在剩余总预算内允许有限重试：

- VBas 建连失败、连接复位和可恢复协议错误。
- VBas HTTP 429、502、503、504。
- 读取超时；使用相同 `TaskID`、`ImageID` 和请求体重试。

默认算子调用最多三次（首次加两次重试），每次失败先释放租约再重新申请。读取超时后原推理可能仍
短时占用 GPU，因此有限重试存在重复计算代价；通过次数上限、实例重选和统一总预算约束该代价。
请求参数错误、图片超限、VBas HTTP 400/422 和可确定的业务校验错误不得重试。

同一请求发生可恢复调用错误后，后续租约申请必须排除该请求中已经失败的实例。若 Control 因负载率
仍返回被排除实例，Gateway 必须立即释放该租约并继续在原容量等待预算内申请，且这次跳过不得消耗
一次真实算子调用尝试。该规则避免失效实例因 `reported_inflight=0` 成为最低负载候选，导致三次调用
全部落到同一失效实例；排除集合只存在于单个请求内，不改变 Control 租约接口和全局路由权威。

### 6. 最终错误码按失败阶段返回

重试成功时 A 服务只收到原算子成功响应。只有确定性错误或预算耗尽才返回业务错误：

- `50301`：确实等待可用在线容量超过允许时间。
- `50302`：Control 在允许恢复时间内持续不可用。
- `50201`：VBas 连接、协议或可恢复 HTTP 错误重试耗尽。
- `50401`：VBas 响应超时重试耗尽。
- `50000`：无法归入上述类型的内部错误。

外层仍返回 HTTP 200，保持现有响应结构。原先笼统的 `50000` 不再解释为“算子过载”；VBas 内部
拒绝应先由 Gateway 重试，只有耗尽后才归入明确错误。

### 7. 结构化可观测性先于继续调参

每次等待和重试记录 `trace_id`、operation、capability、阶段、规范化异常类型、attempt、实例 ID、
已耗时、剩余预算和最终 outcome。指标至少区分 requested、waiting、acquired、rerouted、retry、
timeout、failed、released，并可按在线/离线池与实例汇总。

日志不得记录 Base64、完整请求/响应、OCR/ASR 内容或 embedding。压测报告按业务码统计全部失败，
不能只保留样本后把样本比例当成全量比例。

### 8. 发布采用缓存构建和精确替换

实现和本地回归通过后，在 `192.168.29.11` 记录目标 Git SHA、当前容器完整 ID、镜像完整 ID、配置
摘要和健康状态。构建使用现有 BuildKit 缓存，不使用 `--no-cache`，也不执行 `docker image prune`
或 `docker buildx prune`。

只有全部目标新镜像完成 revision、架构和导入校验后，才逐个替换受影响服务。新容器通过 health、
readiness 和最小真实请求后，精确删除被替换的旧容器和旧镜像；失败时使用发布前记录回滚，旧资产在
新版本门禁通过前不得删除。若实现只修改 Vision 和 Online Gateway，就不构建无关算子；共享包变化
导致镜像内容受影响时按依赖清单扩大范围。

### 9. 压测必须分档、重复并完整收敛

正式 Campaign 使用独立 Run ID 和 task_id，至少包含：

1. Control 重启故障注入：视觉任务已有真实 VBas 批次后，使 Control 暂时不可用 5、15、30 秒；
   每档至少一轮，节点不得失败或重复批次，恢复后全部成功终态。
2. 在线分档：72 并发 5000 次、144 并发 10000 次、200 并发 10000 次；200 并发至少连续三轮，
   每轮业务成功率必须 100%，错误分类计数为 0。
3. 离线基线：20 路全量任务独立执行一轮，四类任务全部成功并完成媒体清理。
4. 最终混合：20 路全量任务与在线 200 并发、10000 次同时开始，至少连续两轮全部通过。

每轮必须等待所有课程任务终态、在线响应完成、租约与 VBas in-flight/queue 归零、Kafka lag 和
Outbox 归零、本轮 `/data/course/{task_id}` 清理完成后才结束。任何测试未完成、驱动中断、证据
缺失或服务容器 ID/revision/config hash 变化，只能标记为中断或环境失效，不能给出通过结论。

### 10. 显存采用冷启动基线、峰值和恢复值三段判定

每组 VBas 测试前重新创建三个 VBas 容器，等待模型 ready 和 5 分钟空闲稳定，取最后 60 秒显存
中位数作为每卡基线。负载期间每 2 秒记录显存、GPU 利用率、功耗、宿主 PID 到容器完整 ID 映射、
接口和在线/离线在途量。终态收敛后继续观察 5 分钟，取最后 60 秒中位数作为恢复值。

负载期间峰值上升本身不等同泄漏；若任一卡恢复值比本轮基线高出 512 MiB 以上，或连续有效轮次的
恢复值单调上升，必须把该轮判为失败并暂停扩大负载。调查须按接口、在线/离线池、请求阶段和实例
关联，检查未释放租约、VBas queue/running、模型框架缓存、请求对象和响应对象生命周期；修复后从
冷启动重新执行失败轮次。若出现 OOM、GPU Xid、容器重启或剩余显存低于 2 GiB，立即停止发压并
保留现场证据。

## Risks / Trade-offs

- [长等待占用 Gateway 连接和内存] → 使用单一 600 秒预算、连接取消传播、连接池和文件描述符预检，
  压测持续采集 Gateway 进程资源。
- [读取超时重试造成同一图片重复推理] → 只允许纯推理接口、保持相同 ID、默认最多两次重试并重选实例。
- [轮询产生惊群效应] → 指数退避、2 秒封顶和随机抖动，后续再评估通知式容量唤醒。
- [PyTorch/CUDA 分配器保留缓存被误判为泄漏] → 使用冷启动基线、终态后稳定观察和跨轮恢复趋势，
  不以单点峰值下结论。
- [新增业务错误码需要 A 服务识别] → 响应字段和 HTTP 形式不变，更新 A 服务对接文档；未知码仍按
  可重试的平台失败处理，正式发布前联合验证。
- [完整混合测试耗时和存储开销较大] → 分档执行、每轮完成清理再进入下一轮，但不得删减最终两轮验收。

## Migration Plan

1. 先补失败分类、预算和重试的单元测试，证明旧实现会失败。
2. 实现共享分类与退避工具、Vision 获取租约恢复、Online Gateway 统一 deadline 和重选实例。
3. 更新 `config.toml` 注释、README、A 服务对接说明、指标和中文 Harness 计划。
4. 完成本地 compile、import、服务测试、跨服务测试和静态检查。
5. 在服务器记录发布前资产，使用缓存构建受影响镜像，校验后精确替换并完成健康与真实请求门禁。
6. 按故障注入、在线分档、离线基线、最终混合的顺序执行；每轮均写入独立不可覆盖证据。
7. 全部验收通过后精确删除旧资产并复查；任一发布门禁失败则回滚到记录的旧镜像和配置。

## Open Questions

无。实现阶段不得擅自放宽 100% 业务成功、完整终态和显存恢复门禁；若服务器客观条件需要调整阈值，
必须先更新本变更并由用户确认，不能在测试结束后为了得到通过结论而修改标准。
