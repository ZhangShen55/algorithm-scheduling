## 背景与动机

当前 `vision_orchestrator_service` 把视觉命令按一次 poll 得到的消息组成封闭批次，必须等待整批全部完成后才再次领取消息；同时单个视觉命令会先把全部抽帧作业排入共享 ffmpeg 信号量，并在整轮抽帧完成后才向 VBas 下发 batch。实测即使将 `kafka.max_poll_records` 从 2 临时提高到 16，仍会出现首条命令独占媒体队列、后续命令已显示“处理中”但 GPU 长时间得不到输入的问题，因此需要把视觉命令消费、媒体抽帧和 VBas 推理改造成有界、可持续补位且跨任务公平的流水线。

## 变更内容

- 将视觉命令 Consumer 从“poll 一批并等待整批结束”改为长期运行的有界在途任务池；任一槽位释放后立即补领下一条命令，不等待同批慢任务结束。
- 明确 `worker.concurrency` 是课程级视觉命令在途上限，`kafka.max_poll_records` 只控制单次拉取数量，二者不再因为封闭批次形成隐含的有效并发上限。
- 将单命令全量抽帧屏障改为有界生产者/消费者流水线：抽帧结果达到 `scan.batch_size` 后立即申请离线租约并调用 VBas，最后不足一批的帧也必须提交。
- 为媒体处理建立跨任务公平的有界调度，避免一个长视频一次性排入数百个 ffmpeg 作业并阻塞其他任务的 ffprobe 和首批抽帧。
- 学生全图、前排和后排分析复用已经抽取的同一组帧文件；区域推理仍保持现有 VBas 请求语义，不重复解码同一时间点。
- 将节点状态原因细化为等待消费、校验本地视频、探测视频、抽帧、等待 VBas 容量、VBas 推理、聚合和结果持久化等可观测阶段；状态码仍沿用既有整数状态机。
- 保持稳定的 `command_id`、领取代次、`batch_id`、帧标识和 Kafka 连续 offset 提交规则，确保重启、重放、失败终态事件和媒体清理不会因为流水线化产生重复结果或状态冲突。
- 补充单元测试、集成测试和 Harness 对照证据，至少验证持续补位、慢任务不阻塞快任务、跨任务抽帧公平、首批推理延迟、失败取消、重启恢复和状态阶段转换。
- 实现验证通过后，在 `192.168.29.11` 使用已有 BuildKit 缓存构建受影响镜像；新容器健康后精确删除被替换的旧容器和旧镜像。按用户要求，本变更不代替用户执行最终业务压力验收。

## 能力范围

### 新增能力

- `vision-orchestration-pipeline`：定义视觉命令持续补位、媒体抽帧与 VBas 推理流水线、跨任务公平调度、细粒度进度状态及恢复一致性要求。

### 修改能力

无。当前主规范未定义视觉流水线吞吐与阶段状态要求，本次以独立能力补充，不改变根级服务目录和部署边界规范。

## 影响范围

- 主要代码：`vision_orchestrator_service/app/infrastructure/runtime.py`、`media.py`、`vbas.py`、`application/analyzer.py`、视觉事件处理与相关配置模型。
- 共享平台：可能调整 `algorithm-scheduling-platform/packages/platform_common/repository.py` 中视觉节点领取后的初始原因，但不改变任务状态码、数据库主键或北向响应字段。
- 配置与文档：`vision_orchestrator_service/config.toml`、README、Compose 运行配置、Harness 场景和部署记录。
- 运行环境：`192.168.29.11` 上的 `vision-orchestrator-service` 镜像与容器；若共享包变更被其镜像打包，只重建实际受影响的服务。
- 兼容性：不改变 A 服务任务提交/查询接口，不改变 VBas HTTP 路径、请求字段、响应字段、离线容量池语义和四服务边界。
