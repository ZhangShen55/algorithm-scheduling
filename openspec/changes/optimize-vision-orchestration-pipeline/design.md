## 现状与约束

`vision_orchestrator_service` 当前只有一个 Kafka Consumer 和一个 Uvicorn Worker。`VisualCommandConsumerLoop.run_once()` 每次 poll 后为本批消息创建任务，但必须等待本批所有任务完成才返回并进行下一次 poll。服务器原配置为 `worker.concurrency=16`、`kafka.max_poll_records=2`，因此每轮最多执行两条视觉命令；当其中一条先完成时，空出的课程槽位也不会补入新命令。

单条视觉命令进入分析后，`FFmpegFrameExtractor.extract()` 会为该轮全部时间点创建协程并共享一个全局 ffmpeg 信号量。按 10 秒采样一节长课会产生数百个时间点，先进入事件循环的长任务可以把自己的全部抽帧作业排在其他命令的 ffprobe 和首批抽帧之前。`VisualAnalyzer._infer()` 还会等待整轮全部图片生成后才调用 `VbasBatchClient.analyze()`，导致 CPU 解码和 GPU 推理呈长时间等待与短时突发交替。

2026-09-04 在 `192.168.29.11` 的受控对照验证保留了两组事实：

- `offline20-20260904T024034Z` 使用 `max_poll_records=2`，约 30 分钟仅 6/20 课程达到全量终态，26 个视觉节点仍显示“视觉节点已领取，正在准备本地视频”。
- `maxpoll16-20260904T033113Z` 临时使用 `max_poll_records=16`。配置能在已有 backlog 时扩大单次领取量，但第一条命令先到时 Consumer 仍只领取一条并等待其完成；后续命令在 Kafka 积压。第一条完成后，多条命令虽被领取，又因同一任务预先排入的抽帧作业阻塞在“准备本地视频”。受控运行到 1005 秒时，PPT、OCR、ASR 均已 20/20 完成，但只有 1/20 课程达到全量终态，学生视觉完成 2 个、教师视觉完成 1 个，另有 37 个视觉节点处于运行态；停止采样时三张 GPU 利用率均为 0%。本轮随后按 task_id 精确清理并恢复 `max_poll_records=2`，不作为正式验收。该结果证明配置调整只能缓解 backlog，不能消除封闭批次和媒体队列的不公平。

本次必须保持 A 服务任务提交和查询契约、VBas HTTP 契约、整数节点状态码、Control 租约权威、四服务边界、现有自适应扫描语义以及 `/data/course`、`/data/result` 生命周期约定不变。

## 目标与非目标

**目标：**

- 视觉命令在 `worker.concurrency` 范围内持续补位，任一慢命令不能阻止空闲课程槽位领取新命令。
- 多课程共享媒体处理资源时具有公平性，单个长视频不能一次性占据所有等待中的 ffmpeg 作业。
- 每个命令的确定性帧批次一旦准备完成就开始 VBas 推理，并与后续批次抽帧重叠。
- 学生全画面、前排和后排推理复用同一时间点的本地图片，不重复解码视频。
- 查询结果能区分真正的等待消费、媒体准备、容量等待、推理和聚合阶段。
- 保持 Kafka 至少一次投递、同 partition 连续 offset 提交、稳定批次身份、失败终态通知和媒体清理语义。

**非目标：**

- 不调整 10 秒粗扫、5 秒与 2 秒细化算法，不修改教师/学生聚合业务规则。
- 不增加 VBas 离线声明容量，不修改 VBas 模型、显存策略或在线容量池。
- 不增加 Kafka partition 或部署第二个 Vision 副本；后续水平扩展另行设计。
- 不改变 A 服务和 VBas 的请求、响应、HTTP 路径或节点整数状态码。
- 不在本变更中重新执行完整业务压力验收；部署后由用户发起，平台只做健康与版本门禁。

## 技术决策

### 1. Consumer 使用跨 poll 的长期在途表

Consumer Loop 持有长期存活的 `in_flight`、每 partition 完成水位和待提交集合，而不是在 `run_once()` 内创建临时集合。循环按以下顺序运行：

1. 回收已经完成的任务并推进每个 partition 的连续提交水位。
2. 计算 `worker.concurrency - len(in_flight)`。
3. 只要存在空闲槽位，就继续 poll 并立即启动最多为空闲槽位数量的命令。
4. 槽位已满时等待任一任务完成，同时继续维持 Kafka 心跳；停止时不再领取新消息。

`kafka.max_poll_records` 仅表示一次 broker 拉取的上限。若一次 poll 返回数量大于即时空闲槽位，剩余消息进入容量不超过 `max_poll_records` 的内存 pending deque；pending 未排空前不再 poll。这样总内存有界，且 `max_poll_records` 小于 `worker.concurrency` 时也能通过连续 poll 填充槽位。

较高 offset 先完成时只登记完成，不越过较低未完成 offset 提交。进程在提交前崩溃可能重放已经完成的高 offset，继续依靠现有命令代次和节点事实保证幂等。选择长期在途表而不是简单把 `max_poll_records` 固定为 16，是因为命令会错峰到达，且慢任务会造成批内队头阻塞。

### 2. 媒体调度以确定性 batch 为单位公平推进

分析器先按排序后的时间点和 `scan.batch_size` 规划确定性 `FrameBatchPlan`。每个计划包含任务、流、扫描轮次、区域身份、batch 序号和有序时间点，但尚不读取图片。媒体层只允许每个活动命令预取有限个 batch，默认上限为 2；全局同时运行的 ffmpeg/ffprobe 进程仍受 `media.max_concurrent_processes` 限制。

调度器在活动命令之间轮转选择下一个 batch，不允许某一命令一次性提交整节课的全部时间点。ffprobe 使用单独的短作业入口或预留至少一个媒体槽位，避免被数百个抽帧作业饿死。队列容量必须由活动命令数、每命令预取 batch 数和 batch 大小推导并有硬上限。

选择 batch 级公平调度而不是继续依赖 `asyncio.Semaphore` 的协程排队顺序，是因为 Semaphore 只限制正在运行的进程，不限制等待协程数量，也不提供跨任务公平保证。

### 3. 抽帧生产者和推理消费者通过有界队列衔接

每条视觉命令创建一个受其生命周期约束的生产者：按确定性 batch 计划抽取图片，将已完整准备的 batch 放入容量为 2 的队列。消费者取得首个 batch 后立即构造稳定的 VBas 帧身份、申请 Control `offline` 租约并下发，不等待该轮后续 batch。生产者可在 VBas 推理期间继续准备下一批，从而重叠 CPU/磁盘解码与 GPU 推理。

最后不足 `scan.batch_size` 的 batch 必须正常提交。结果按时间戳写入映射，最终聚合前校验计划时间点和响应一一对应。batch 分组、顺序和身份只由输入时间点与区域身份决定，不受协程完成顺序影响，保证同一命令重试时 `batch_id` 稳定。

若某批失败，命令级取消域会停止生产者、取消尚未开始的媒体作业、终止本命令启动的子进程、释放已取得租约并等待已启动清理完成；不得取消其他课程。实现优先使用可取消的 asyncio 子进程，而不是无法及时终止的 `asyncio.to_thread(subprocess.run)`。

### 4. 学生帧资产与区域推理解耦

学生任务只生成一次按时间点组织的帧资产。每个已准备 batch 依次执行全画面、前排和后排中实际需要的区域推理，三种区域继续使用不同 `image_id`/`batch_id`，但引用相同的本地图片文件。下一批抽帧可与当前批区域推理并行；同一批区域推理的并行程度仍由现有 VBas 离线租约限制。

没有 `front_points` 或 `back_point` 时不创建相应区域工作，继续使用既有兜底聚合规则。此调整不改变 VBas 请求字段或学生结果结构。

### 5. 状态码稳定，阶段原因真实反映执行位置

保留 `WAITING(10)`、`RUNNING(50)`、`SUCCEEDED(60)` 和 `FAILED(70)` 等现有整数状态。Orchestrator 发布视觉命令后使用“视觉命令已发布，等待 Vision 消费”，不得表述为已经领取。Vision 消费并验证命令代次后，按阶段更新中文原因：

- `正在校验本地视频`
- `正在探测视频时长`
- `正在抽取采样帧（已完成 batch/总 batch）`
- `正在等待 VBas 离线容量`
- `正在执行 VBas 推理（已完成 batch/总 batch）`
- `正在聚合教师行为区间` 或 `正在聚合学生人数和行为结果`
- `正在持久化视觉结果`

阶段切换必须立即写入；同一阶段的批次进度采用去抖更新，避免每帧写数据库。查询响应沿用现有 `reason` 和进度字段，不增加 A 服务必传字段。

### 6. 指标与日志验证持续供给而不是只看终态

增加或完善以下低基数指标：视觉命令 pending/in-flight、命令槽位利用率、媒体队列深度、各任务首批抽帧等待、首个 VBas 请求延迟、已准备/已推理 batch 数、VBas 容量等待时间。日志携带 `task_id`、`node_id`、`command_id`、扫描轮次、区域、batch 序号和阶段，不记录图片、完整响应或模型结果。

本地集成测试使用可控慢任务证明：一条慢命令存在时，其他空闲槽位仍领取后续命令；一个长视频的后续 batch 不得排在所有其他任务首批 batch 之前。Harness 保留 `max_poll_records=2` 和临时 `16` 的对照证据及其未完成/失败事实，不把临时改善写成正式验收通过。

### 7. 发布只替换实际受影响镜像

实现和本地验证完成后记录 `192.168.29.11` 当前容器 ID、镜像 ID、配置摘要和回滚标签。使用已有 BuildKit 缓存构建新的 `vision-orchestrator-service`；若共享包或 Orchestrator 的等待原因代码发生变化，则同时构建 `orchestrator-service`。不使用 `--no-cache`，不执行全局 prune。

新镜像完成 revision、x86_64 架构和导入检查后逐个替换容器，只执行 health/readiness、Kafka Consumer 正常和版本一致性门禁，不替用户运行最终压力测试。新容器正常后精确删除被替换的旧容器和旧镜像；门禁失败则恢复原镜像和配置，旧资产在成功前不得删除。

## 风险与权衡

- [16 个课程同时预取导致图片和协程数量增长] -> 每命令只预取有限 batch，所有 pending 与 ready 队列均有硬上限。
- [多任务公平降低单课程最快完成时间] -> 以整体 GPU 持续利用率和多课程尾延迟优先，单任务场景仍可使用全部空闲媒体槽位。
- [异步完成使 Kafka offset 提交复杂] -> 按 partition 维护连续水位，覆盖乱序完成、取消、重启和 rebalance 测试。
- [流水线失败留下 ffmpeg 子进程或租约] -> 使用结构化取消域、可取消子进程和 `finally` 释放；测试进程、租约和临时文件归零。
- [阶段进度写入过于频繁增加数据库压力] -> 阶段必写、批次进度去抖并设置最小变化阈值。
- [临时 `max_poll_records=16` 被误认为最终修复] -> Harness 和配置说明明确其仅为诊断对照；正式验收以持续补位和首批延迟测试为准。

## 迁移与回滚

1. 固化旧配置与临时 `max_poll_records=16` 对照证据，停止并清理独立测试任务，不覆盖历史证据。
2. 先补 Consumer 持续补位和连续 offset 单元测试，再重构长期在途表。
3. 补媒体公平调度、流水线、帧复用、取消与稳定 batch 身份测试，再实现媒体和分析器改造。
4. 细化阶段原因、指标、README、`config.toml` 注释和 Harness。
5. 完成 compile、import、相关服务测试和跨服务集成测试。
6. 在服务器缓存构建并替换受影响容器，通过最小部署门禁后删除精确旧资产。
7. 若部署失败，恢复记录的镜像、配置和容器；数据库不需要结构迁移，回滚不改写已有任务事实。

## 待确认问题

无。最终业务压力测试由用户在新容器部署后执行；若测试继续显示 GPU 空闲，应以新增的首批延迟、媒体队列和命令槽位指标定位，不再仅通过扩大课程并发猜测。
