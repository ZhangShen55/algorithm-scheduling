## 为什么

真实全量任务 `test_all_0903_11` 暴露出两个视觉批次调度缺陷：一次未到达 VBas 的瞬时 HTTP 异常会直接终结整个学生行为节点，教师多阶段扫描又会为不同帧集合重复生成 `t-0000` 等批次标识，导致租约审计表现为同一工作反复获取。与此同时，Vision 固定允许 16 个批次协程竞争当前仅 3 个离线槽位，未与已注册 VBas 的真实离线容量一致。

## 变更内容

- Vision 的有效 VBas 批次并发动态取所有可调度 VBas 实例 `offline` 容量之和；在当前三实例且每实例 `MaxConcurrentOfflineBatches=1` 时有效并发为 3，而不是固定 16。
- Control 租约继续作为最终原子准入；Vision 的本地容量门控用于避免超过集群离线容量的协程持续轮询，不替代租约和负载均衡。
- VBas 逻辑批次 ID 根据任务、流类型、区域身份和帧集合稳定生成；不同扫描阶段或不同帧集合不得复用同一 ID，相同逻辑批次重试必须保持同一 ID。
- 对连接、读写和超时等瞬时 VBas HTTP 故障执行配置化有限重试，每次尝试重新申请租约；业务 4xx、非法响应和明确业务失败不重试。
- 错误原因始终包含异常类型、实例、逻辑批次和尝试次数，禁止再出现空失败原因。
- 增加容量、批次身份、瞬时失败恢复和真实故障样本的测试与 Harness 记录。

## 能力

### 新增能力

- `vision-vbas-batch-dispatch`: 规定 Vision 到 VBas 的动态离线容量门控、稳定逻辑批次身份、有限重试和可观测错误语义。

### 修改能力

无。

## 影响

- 影响 `vision_orchestrator_service` 的 VBas 客户端、容量快照读取、配置、运行时组装和测试。
- 读取 `control-service` 现有 `/ops/operator-instances/snapshot` 接口，不改变租约接口和 Redis 权威关系。
- 不改变 A 服务任务提交/查询接口，不改变 VBas 教师/学生 HTTP 路径、请求字段和响应字段。
- 后续远端部署只需重建并替换 `vision-orchestrator-service`；VBas 算子代码和镜像不因本变更修改。
