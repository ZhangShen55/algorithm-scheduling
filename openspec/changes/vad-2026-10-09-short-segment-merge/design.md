## Context

v1.0.2 和 v1.0.3 已经使用连续 VAD、精确 PCM 切分、pending PCM 和 pre-roll。当前会话在每次收到有效 VAD end 后立即调用 `finalize_segment()`，因而 VAD 在连续语音中返回的多个短结束会直接变成多个 `finished=true`。

在教师1 全量结果中，B 路有 889 个 finished，其中 528 个的时长不超过 0.5 秒。用户提供的 `segment-000052` 至 `segment-000056` 在 0.48 秒左右的间隔内连续开始，是应用层应对短暂停顿的典型场景。

## Goals / Non-Goals

**Goals:**

- 将 VAD end 从“立即字幕结束”改为“候选语句结束”，避免短间隔内的语音被切成多段。
- 在下一个 VAD start 在合并窗口内出现时，使用同一 `key` 继续当前语句，并在最终纠正时一次性使用完整 PCM上下文。
- 保证每个真正完成的语句仍只发送一次 `finished=true`，并保持 `bg/ed` 单调、不倒退、不重叠。
- 保留上游 0.48 秒分块、pending PCM、150 ms 左右 pre-roll、约 20 秒最大段长保护和现有响应格式。
- 用合成测试和教师音频短片段测试验证细碎断句减少、纠正上下文完整、延迟有界。

**Non-Goals:**

- 不修改 v1.0.1 路由、`online_gateway_service` 或上游请求方式。
- 不改变 `key`、`text`、`finished`、`bg`、`ed` 字段、类型或 WebSocket 路径。
- 不通过简单地累计三个 finished、依赖标点符号或更换 ASR/VAD/纠正模型解决断句。
- 不引入需要改变客户端协议的 EOS 字段。

## Decisions

### 1. 使用候选 end 状态而不直接 finalize

会话增加 `candidate_end_sample`。VAD 返回 end 时只记录候选结束点，当前 `segment_key` 不重新生成，也不立即发送 `finished=true`。等待期间可继续发送同 key 的临时结果，但不执行终端纠正。

如果下一个 VAD start 与 candidate end 的音频时间差不超过 `vad_merge_max_gap_ms`，则清除候选 end，保持同一 key 继续累积。这会将用户例子中的多个短语音段合并到一个终端纠正输入中。

### 2. 用音频时间限制候选窗口

首次基准使用 `vad_merge_max_gap_ms = 720`，约为 1.5 个上游分块。如果候选 end 之后已收到的音频超过该窗口仍没有新 start，则在下一个处理点 finalize，不会无限等待。

使用音频时间而不是客户端时钟，可以避免快速发送或远端推理较慢时断句行为不一致。

### 3. 硬切段优先于合并

达到约 20.16 秒最大段长时，必须立即完成强制切段，清除 candidate end 并发送 `finished=true`。合并窗口不能让单段无界限增长。

### 4. 保持实时字幕语义

候选期间的临时结果使用原 key 和当前可见文本；只有当候选窗口结束或硬切段时才发送 `finished=true`。不缓存多条已完成字幕再一次批量输出。

### 5. 可配置且可回滚

在 `config.toml` 中增加合并窗口参数，保留 1000 ms VAD 参数作为默认基线。参数非法或不为正数时启动校验失败。如果细碎切分在特定音频上反而增加，可通过回滚合并参数恢复旧行为，而不需改动协议。

### 6. 对比测试以时间轴和断句质量为主

测试必须比较当前 1000 ms、1200 ms 和 1000 ms + 合并窗口三种方案，记录 finished 数、0.5 秒以下段数、首次和平均 finished 延迟、纠正次数、文本重复、`bg/ed` 倒退/重叠和协议字段。没有人工标注真值时，不能仅凭文本长度判断准确率。

## Risks / Trade-offs

- [风险] 相邻的两个真实短句可能在合并窗口内被合并。→ 用可配置窗口、教师音频回放和 1000/1200 ms 对照调参；默认不超过 720 ms。
- [风险] `finished=true` 最多增加一个合并窗口的音频延迟。→ 用音频时间进行有界判断，并在 summary 中记录延迟。
- [风险] 合并后的 PCM 输入更长，纠正模型耗时可增加。→ 继续使用约 20 秒硬保护，并监控最大纠正等待。
- [风险] 客户端旧逻辑可能依赖快速 finished。→ 字段不变，只增加最多 720 ms 的有界延迟，并使用现有协议测试验证。

## Migration Plan

1. 先在 Mac `asr` 环境增加候选 end 状态、配置校验、合成 VAD 跨块测试和教师音频 30 秒基准。
2. 使用 `ssh server12` 同步代码，在 `cuda:0` 上启动单个远端实例。
3. 按 v1.0.2 、v1.0.3 顺序执行短测，再按原有全量验收方式执行 A/B/C 顺序全量测试。
4. 如果细碎断句没有减少或延迟超过阈值，调整合并窗口或回滚参数，不改变协议。
5. 测试结束后关闭 `server12` 后端，确认 8084 释放和 GPU 显存回收。

## Open Questions

- 默认合并窗口最终采用 600 ms、720 ms 还是 800 ms，需通过同一段教师音频测试确定。
- 是否需要将合并后的重识文本和之前临时文本做重复字合并，需根据 v1.0.2 实际模型输出验证。
